# Windows KVM performance changes (branch `kvm-perf`)

Based on upstream `26846b1c7f`. Only the Windows KVM (`meshcore/KVM/Windows`) and the
x64 configurations of `meshservice/MeshService-2022.vcxproj` are changed; the protocol
and the server are unchanged.

1. `kvm.c`: the capture loop runs with `timeBeginPeriod(1)`, so the frame-rate
   pause is not rounded up to the 15.6 ms system tick (links `winmm.lib`). When tiles
   were sent, the frame work time is subtracted from the frame-rate timer.
2. `tile.cpp`: the capture bitmap is reused between frames. When scaling, the
   screen is captured at full resolution into a DIB section (no `GetDIBits`) and
   downscaled on the CPU with an area-average filter: SSE2 fast paths for 50% (2:1)
   and 75% (4:3), a table-based filter for other ratios. The visible screen area is
   mapped to the visible scaled area (`StretchBlt` mapped the tile-padded sizes,
   stretching the image vertically by ~1%). `StretchBlt` is only a fallback;
   `KVM_STRETCH_MODE` selects its mode (default `HALFTONE`).
3. `tile.cpp`: on x64, JPEG tiles (types 1 and 4) are encoded with the
   TurboJPEG 3 API directly from the desktop buffer instead of GDI+.
   PNG/TIFF and other pixel formats still use GDI+. `KVM_TJ_SUBSAMP` selects
   chroma subsampling (default `TJSAMP_444`, sharp colored text).
4. `kvm.c`: the screen is captured on a separate thread. GDI capture is paced by
   DWM composition (frame times are multiples of 16.7 ms), so while the screen is
   changing the next frame is captured while the current one is encoded and sent.
   When nothing changes the loop stays sequential (same idle CPU use and latency).
   The geometry (resolution, scaling, desktop) is only changed by the main loop while
   the capture thread is idle; frames captured with an older geometry are dropped.

Measured on a Ryzen 5 5500U laptop, 2160x1440 at 60 Hz, JPEG q70, frame-rate
timer 20 ms, screen changing continuously:

| scaling | upstream | `kvm-perf` |
|---|---|---|
| 100% | ~14.5 FPS | 30 FPS |
| 75%  | ~12 FPS   | 30 FPS |
| 50%  | ~15 FPS   | 30 FPS |

30 FPS is the limit of GDI capture on that machine (`BitBlt` takes ~28-31 ms).

## libjpeg-turbo

The library is not part of this repository. Install/extract the official
libjpeg-turbo 3.x **VC x64** build
(https://github.com/libjpeg-turbo/libjpeg-turbo/releases) so that these exist:

    C:\libjpeg-turbo64\include\turbojpeg.h
    C:\libjpeg-turbo64\lib\turbojpeg-static.lib

A different location can be passed with `msbuild /p:TurboJpegDir=<dir>`.
Only the `Release|x64` and `Debug|x64` configurations of
`MeshService-2022.vcxproj` use it (they define `_TURBOJPEG`).

## Build

    msbuild MeshAgent-2022.sln /m /t:MeshService-2022 /p:Configuration=Release /p:Platform=x64

The output is `Release\MeshService64.exe` (not signed). Compile-time options can be
passed through the `CL` environment variable, e.g. `set CL=/DKVM_TJ_SUBSAMP=TJSAMP_420`.

## Deploying to a MeshCentral server

Put the binary in `meshcentral-data/agents/MeshService64.exe` and restart the server;
agents with automatic updates enabled update themselves. The server then serves this
file instead of its bundled agent (and no longer offers official agent updates) until
the file is removed.

## 5. DXGI Desktop Duplication (WA-1)

Only `meshcore/KVM/Windows` and the x64 configurations of `meshservice/MeshService-2022.vcxproj` (plus the
workflow `.github/workflows/kvm-perf-release.yml`, see docs/releases.md) are changed; the protocol and the server are not.

**Behaviour.** On x64 (`MeshService-2022`, `Release|x64` and `Debug|x64`, macro `KVM_DXGI`) the capture thread keeps the screen in the
full resolution bitmap and updates it from `IDXGIOutputDuplication`: only the rectangles that DXGI reports as changed (and the
destinations of moved rectangles) are copied from the GPU, through a staging texture or, when the driver keeps the desktop image in
system memory (`DesktopImageInSystemMemory`, e.g. virtual machines), straight from the mapped surface. The result is a normal BGRA
buffer, so scaling and tile encoding are unchanged. A frame is `FULL` (every tile goes through the CRC check, as with GDI), `PARTIAL`
(only the tiles that touch the changed rectangles are checked) or `UNCHANGED` (nothing is copied, compared or encoded; the loop waits
in `AcquireNextFrame`, so an idle screen costs almost no CPU). Moved rectangles are only counted and logged, they are copied as ordinary changes (no CopyRect).
The mouse cursor is not part of the DXGI image: at 100 % it is drawn into the output like the GDI path does (`mouseMove[0] != 0`),
otherwise the cursor messages of the protocol are used as before.
`DXGI_ERROR_INVALID_CALL` from `AcquireNextFrame` (seen on Hyper-V after a mode change) is a transient failure (no penalty, 500 ms); three in a row without an image count as an error. GDI is used automatically when: `DuplicateOutput` fails or `d3d11.dll`/`dxgi.dll` are missing (they are loaded at run time, nothing is added
to the imports), Windows 7 (no `IDXGIOutput1`), the capture rectangle is not exactly one output (all screens of several monitors), a rotated output,
scaling up, and after `DXGI_ERROR_ACCESS_LOST` until the duplication is created again (250 ms; more than 5 times a minute: 5 s). Three failures in a row on
the default desktop switch DXGI off (since GDI with a retry after a pause, section 11); a failure on another desktop (logon screen, UAC) is not counted, DXGI is tried again when the
desktop changes. DXGI calls run under `__try/__except`: an exception switches DXGI off for the process.

**Switches.** `/DKVM_DXGI_DISABLE` (compile time, e.g. `set CL=/DKVM_DXGI_DISABLE`, workflow input `extra_cl`) builds the GDI path (the log stays);
`MESH_KVM_FORCE_GDI=1` in the environment of the service (the KVM child inherits it: `HKLM\SYSTEM\CurrentControlSet\Services\<service>\Environment`,
REG_MULTI_SZ, then restart the service) forces GDI at run time.

**Log.** `<directory of the exe>\<exe name without .exe>-kvm.log`, one line per event and one `stats` line per 10 s (limit 1 MB, then nothing is appended).
**The log is off by default.** The statistics are always collected (the adaptive quality below depends on them), but the file is written only when `MESH_KVM_STATS_LOG=1` is in the environment of the service (system environment variable, then restart the service), or in builds with `/DKVM_STATS_LOG_ALWAYS`. Lines:
`start build=... dxgi=<0|1> env_force_gdi=<0|1>`, `dxgi open adapter=... mode=... sysmem=<0|1> desktop=<name>`, `dxgi lost|fail|ineligible|disabled|slow_init|lost_storm|stale...`,
`stats t= period_ms= path=<dxgi|gdi|mixed> frames= full= partial= unchanged= fps= ... copy_us_avg= out_us_avg= capture_us_avg= write_ms= dirty_rects= move_rects= ...`.
`frames` counts every iteration of the loop (also `unchanged`): the picture rate is `fps = (full + partial) / period`. `copy_us`: GPU -> persistent image,
`out_us`: copy of the whole image and the cursor (or scaling) into the frame buffer, `write_ms`: time blocked in the write to the pipe.
Every 10 s, when DXGI reported no change for a second, the persistent image is compared with a fresh GDI capture outside the cursor (`stale_*`);
two differences in a row (`dxgi stale`) re-create the duplication; if the difference is still there after that (`dxgi stale_systematic`, e.g. HDR) the check only measures and logs until the pictures agree again (since the capture source choice not for the rest of the process; and a duplication that never delivers an image is told from this case, section 11).

**Tool.** `meshcore/KVM/Windows/tools/kvm_dxgi_check.cpp` (built by the workflow as `kvm-dxgi-check.exe`, not part of the agent): `info`, `compare`, `rects`, `cursor [--ibeam]`, `pointer [seconds] [--move]`, `idle`, `stalecost`.

**Software cursor in the DXGI image.** On some virtual machines (Windows 10 LTSC on a VirtIO GPU display driver or the Microsoft Basic Render Driver, `sysmem=1`) the system composes the
mouse cursor into the desktop image that Desktop Duplication delivers; the GDI path never contained it. The viewer draws its own pointer, so it showed twice. Not every machine without a GPU does it
(a Windows 11 Hyper-V machine with the same adapter does not), so the detection does not look at the adapter. `kvm-dxgi-check pointer [seconds] [--move]` showed what DXGI says
(`PointerPosition.Visible` with `LastMouseUpdateTime != 0` is **not** a usable signal): with a software cursor the duplication reports no pointer at all (no frame with `LastMouseUpdateTime != 0`, also while the
cursor moves) and the cursor field differs from GDI by 140-290 pixels; with a hardware cursor (a laptop with an AMD GPU) or a hypervisor that delivers the pointer (a Windows 11 VM) pointer updates with `Visible = TRUE` arrive within a second and the field is identical to GDI
(`Visible = FALSE` updates also occur on hardware while `CURSOR_SHOWING` is set, so that combination says nothing).
*Detection:* the agent latches "hardware" at the first pointer update with `Visible = TRUE` (nothing is examined or done until the duplication is opened again); until then, for every image frame with the
cursor showing at a position or with a handle not examined yet, the cursor field (cursor bitmap at its hotspot plus `KVM_DXGI_POINTER_MARGIN` = 24 px) of the persistent image is compared with a GDI read, and at least
`KVM_DXGI_POINTER_MIN_DIFF` = 8 differing pixels mean "embedded".
*Taking the cursor out without reading the screen per frame* (a GDI read of the screen costs 16-30 ms on these machines whatever its size: `kvm-dxgi-check bltcost`, 80x80 field 20 ms, whole 1280x720 screen 28 ms;
a version that read the field after every frame lost 39 % of the pictures/s in the `video` scenario). Invariant: the persistent image never holds the cursor. A hook in `dxgi_capture_acquire` (`dxgi_capture_set_precopy`) lets the agent save the cursor field of
the persistent image (S) just before a frame that touches it is copied in; afterwards the pixels under the shape of the cursor are put back from S, the rest of the field keeps the new DXGI pixels. The shape is a mask per cursor handle (8 handles cached):
the pixels that differ between a DXGI image and a GDI read, widened by one pixel (`dxgi_ptrmask.h`, host test `tools/test_ptrmask.cpp`). Where the content under the cursor changed, those pixels are out of date; a GDI read of the field (`SRCCOPY`) puts the truth
under the mask `KVM_DXGI_POINTER_QUIET_MS` (150) after the last frame that touched the field, or every `KVM_DXGI_POINTER_REFRESH_MS` (500) while frames keep touching it (video under the cursor); a read in a quiet moment also adds what the mask missed
(shadow; not animated cursors: the mask and the sprite come from step 0 of the animation, so while a busy cursor animates its parts outside that mask can stay in the picture) and replaces a provisional "whole field" mask (more than 60 % of the field, or a field cut by the screen edge, or content changing during the first read). A cursor handle without a mask costs one GDI read.
Fixes after the review (WA-2b round): (1) the field of a *still* cursor that a frame touched is marked out of date also when nothing outside the mask changed (a change entirely under the shape is put right by the next GDI read: after `KVM_DXGI_POINTER_QUIET_MS` of calm or every `KVM_DXGI_POINTER_REFRESH_MS`); a moving cursor over static content still costs no read. (2) `pm_find` gives the best match of every saved rectangle and `pm_pick` takes the one nearest to the expected places (GetCursorInfo and the last places where it was found; a full match within `KVM_DXGI_POINTER_NEAR_PX` = 128 pixels ends the search; at most 600 000 positions per frame); the refresh of an out-of-date field no longer requires that GetCursorInfo points to the place of the last restore (the GDI read has no cursor in it, so what goes under the mask is true wherever the cursor is). (3) `pm_sprite_spread` is a permutation for every n (the stride is coprime with n). (4) the buffer N is written only in the branches that set the field; of the small rectangles of a frame the ones near the cursor windows are saved first (at most `PM_REGIONS` = 16 are saved).
A moving cursor over static content, and a still screen, need no GDI read. The hardware path (a Windows 11 VM, a laptop with an AMD GPU) does no extra work per frame.
Log: `dxgi pointer embedded=<0|1> reason=probe|probe_clean|hardware_pointer ...`, `dxgi pointer mask reason=probe|new_cursor|quiet ... pixels=`, and in `stats`: `ptr_embedded= ptr_restores= ptr_gdi_reads= ptr_gdi_us_avg= ptr_mask_px=`.
`/DKVM_DXGI_POINTER_KEEP` switches it off (the detection stays). Things to know: (1) the GDI read must not use `CAPTUREBLT`: on the Basic Render Driver every such read made the system draw the cursor again, a new DXGI image
for every read (13 images/s from a still screen, `kvm-dxgi-check pointer 5 --blt=capture`; `--blt=plain` gives none); without it layered windows (shadows, fading menus) that overlap the cursor field are missing from the pixels under the cursor until DXGI reports the area again.
(2) While content changes under a stationary cursor, the pixels under its shape are up to 500 ms out of date (a cursor-shaped patch of the older picture). (3) A frame composed with the cursor in A while the field is taken at B leaves a trace in A until the next frame (which reports A as changed); no trace outlives the last frame.
(4) The cursor drawn by the agent itself for the legacy overlay (XOR pointer, `mouseMove[0] != 0`) is unchanged; it is drawn into the copy of the image. (5) The state is lost when the duplication is closed; a cursor that is hidden or on another monitor is not handled.
Measured on the Windows 10 VM (1280x720, `video`, n = 3 x 10 s): 31.34 pictures/s (31.27-31.39), 787 KiB/s, echo 57 ms; GDI reads 13-15 per 10 s (28-30 ms each, about 4 % of the time), 150-180 restores per 10 s.
*A moving cursor (found in the frame, not asked for).* The system composes the cursor into a frame at the place where the pointer was when the frame was made; `GetCursorInfo`, asked afterwards, already gives a newer
place (measured with `kvm-dxgi-check trail --move`, a pointer moved every 10 ms on a 1280x720 virtual machine: in 124 of 125 frames the composed cursor was **not** where `GetCursorPos` said, it was 1-3 steps (10-30 ms) behind).
Restoring the background at the place `GetCursorInfo` gives therefore left the cursor in the image while the pointer moved (the lower the frame rate, the longer it showed) and a trace that stayed after it stopped. The same measurement showed that
DXGI reports one small rectangle per frame (the visible shape of the cursor at its old and its new place together: 124 of 125 frames at most 48 pixels on a side, none above 96). So the hook (`dxgi_capture_set_precopy`) saves the pixels of every
small rectangle of the frame (and, in a large rectangle, windows of 48 pixels around the places where the cursor can be: the one `GetCursorInfo` gives and the last three where it was found), and after the copy the cursor is searched in those regions by
its fully opaque pixels (`kvm_cursor_sprite`: the cursor drawn over black and over white by `DrawIconEx`; `pm_find`, exact comparison with a strict start: found in 125 of 125 frames, 40 microseconds on average, 4000 positions; no second match in the generator picture. A real picture can hold a second one, for instance the same arrow inside a screenshot shown in the frame: of several candidates the one nearest to where the cursor is expected wins, see the next paragraph). The mask of a
colour cursor is made from its bitmap (every pixel with alpha > 0, widened by one pixel), so a new cursor handle needs no GDI read. Monochrome cursors (I-beam) cannot be found by colour; they keep the position of `GetCursorInfo` and the GDI mask.
If the cursor is not found although the frame touched the field at the `GetCursorInfo` position (`ptr_not_found`), the restore is done there and the field is marked stale (a GDI read in a quiet moment, as before).
Test: `rtrail` (kvm-bench-dxgi-correct.spec.js) moves the remote pointer every 10 ms for 4 s over a still picture and compares canvas snapshots taken during the motion with a clean one; `rtrailc` does it over a changing picture by searching the snapshots for the shape of the arrow.
Measured, agent `717a3dc`, Windows 10 VM 1280x720: `rtrail` 0 differing pixels in every snapshot and afterwards, at a frame timer of 30 and of 100 ms (the build before it: 429-1274 differing pixels in the snapshots and 1573 afterwards at 30 ms); `ptr_found` 207 of 212 frames
over moving content, search 140-230 microseconds per frame in `video` (up to 440 with a large rectangle), `video` 31.57 pictures/s (31.45-31.78).

generator in its own window, JPEG q80, 100 %, frame timer 30 ms, 10 s per run, n = 3, mean (min-max). CPU is the `-kvm` child as a share of one core.

## 6. Quality that depends on motion, sharpening and the congestion regulator (WA-2)

Files: `kvm_adapt.h`, `kvm_adapt.cpp` (new), hooks in `tile.cpp`, `tile.h`, `kvm.c`; the protocol and the server are not changed (a sharpened tile is an ordinary picture command).
Active only in the x64 `MeshService` build with TurboJPEG (`KVM_ADAPT_ENABLED` = `_TURBOJPEG` && `KVM_STATS_LOG` && not `KVM_ADAPT_DISABLE`), for JPEG types 1 and 4 with 24/32 bit pixels.
In every other build (x86, ARM64, MeshConsole, GDI+ without TurboJPEG) the functions are stubs: every tile is "full class", nothing is sharpened, the frame pause is the frame-rate timer, i.e. the behaviour of WA-1.

**Behaviour.**
1. *Motion class.* A tile whose content changed in at least `KVM_ADAPT_MOTION_STREAK` (2) frames in a row, each change at most `KVM_ADAPT_MOTION_MS` (250 ms) after the previous one, while at least
   `KVM_ADAPT_MOTION_TILES` (16) tiles changed in the previous frame, is sent with JPEG quality `min(quality of the user, KVM_ADAPT_Q_MOTION = 50)` and 4:2:0 chroma subsampling. Typing and a blinking cursor stay in the full class (sharp).
   `get_tile_at` joins neighbouring tiles into one rectangle only within one class; a changed neighbour of another class is marked for sending by itself (never "don't send": a change must not get lost).
2. *Sharpening.* A tile that was sent lossy (motion class) and has not changed for `KVM_ADAPT_SETTLE_MS` (150 ms) is encoded again from the current picture with the quality of the user and the normal subsampling, in runs of up to `KVM_ADAPT_SHARPEN_RUN` (8) tiles of a row,
   at most `KVM_ADAPT_SHARPEN_BYTES` (96 KiB) per frame (a quarter at regulator level >= 4, a half at levels 1-3). When the content of the screen has not changed for `KVM_ADAPT_SETTLE_MS` and a lossy tile is due, the capture is asked for an image (`KVM_CAPTURE_WANT_IMAGE`): it waits for a new frame as usual (`KVM_DXGI_TIMEOUT_MS`) and, if none comes, returns the unchanged persistent image with an empty change map, so that an idle screen is still sharpened (about 0.2-0.25 s after the last change of the screen). While the screen changes the flag is not set. A tile that changes again before it is sharpened is simply handled as a normal change.
3. *Congestion regulator* (one per KVM session of the process, i.e. one for all viewers of that desktop). The signal is the share of the time the loop is blocked in the write to the pipe, in windows of `KVM_ADAPT_WINDOW_MS` (500 ms): at or above `KVM_ADAPT_CONGEST_PCT` (15 %) the level goes up (max 5),
   after `KVM_ADAPT_CALM_WINDOWS` (3) windows at or below `KVM_ADAPT_CALM_PCT` (3 %) it goes down. Level 1-3: motion quality 40 / 30 / 20 (step `KVM_ADAPT_Q_STEP` 10, floor `KVM_ADAPT_Q_MOTION_MIN` 20), and a tile that is only sent again after a refresh (REFRESH, new geometry) is also sent in the motion class and sharpened later.
   Level 4-5: additionally the frame pause is multiplied by 2 / 4 (at most `KVM_ADAPT_MAX_PAUSE_MS` 250 ms) and, while the output of the loop exceeds `KVM_ADAPT_RATE_FRACTION_PCT` (70 %) of the rate that the link accepted while it was saturated (a token bucket, measured from the write-block windows), the pause is stretched, at most to `KVM_ADAPT_MAX_PAUSE_MS`. This does not cap the output at 70 %: the capture still runs at least 4 times a second and a debt of more than 2 s of tokens is forgiven, so that a full refresh can never be starved.

**Switches.** `/DKVM_ADAPT_DISABLE` (compile time; workflow input `extra_cl`) builds the WA-1 behaviour (the log stays). `MESH_KVM_ADAPT=0` in the environment of the service (same registry value as `MESH_KVM_FORCE_GDI`, then restart the service) switches it off at run time. Every threshold above can be overridden with `/D<NAME>=<value>`.

**Log** (same file as WA-1): `adapt start enabled=<0|1> reason=<on|env> q_user=.. type=.. q_motion=.. motion_ms=.. settle_ms=..` (`q_user` is the quality before the settings of the viewer arrive; the quality used is the live one),
`adapt level from=.. to=.. block=<x.y>% accept_kbps=.. q_motion=.. since_start_ms=..`, `adapt rate_cap kbps=..`, and one `adapt stats` line after every `stats` line:

(a separate line instead of extra fields of `stats`, so that the WA-1 line keeps its format). With `MESH_KVM_ADAPT=0` the levels are still computed and logged, but have no effect.

One regulator for all viewers of the desktop: with several viewers the slowest one decides. ## 7. Bandwidth budget, motion frame limit and JPEG tables (WA-2b)

Files: `kvm_adapt.h`, `kvm_adapt.cpp`, hooks in `tile.cpp`, `tile.h` (field `deferred`), `kvm.c`. Same scope as WA-2 (x64 `MeshService` with TurboJPEG, JPEG types 1 and 4). The server is not changed; the protocol gets one optional field (bytes 10-11 of command 5, the budget chosen by the viewer, added at the owner's request, see "Who sets the budget"); a viewer that does not send it, and an agent that does not know it, work as before.
`/DKVM_ADAPT_DISABLE` and `MESH_KVM_ADAPT=0` switch all of it off together with WA-2.

**Budget.** The bytes written to the pipe in each 500 ms window of the regulator (the picture packets: motion rectangles, full rectangles, sharpening; the few small packets of cursor shapes and displays are not counted) are compared with `KVM_ADAPT_BUDGET_KBPS` (default 0 = no budget; see "Who sets the budget" below).
A ladder of steps B0..B7 sets the quality of the motion class, the scale of the picture and the frame limit of the motion class (the quality is never raised above the quality of the user):

| step | motion quality | scale of the picture (share of the viewer's scale) | motion frame limit |
|---|---|---|---|
| B0 | `KVM_ADAPT_Q_MOTION` (50) | 100 % | none (loop pace) |
| B1 | `KVM_ADAPT_BQ1` (40) | 100 % | none |
| B2 | `KVM_ADAPT_BQ2` (40) | 100 % | `KVM_ADAPT_BF2` (30 frames/s) |
| B3 | `KVM_ADAPT_BQ3` (30) | 100 % | `KVM_ADAPT_BF3` (30) |
| B4 | `KVM_ADAPT_BQ4` (25) | 100 % | `KVM_ADAPT_BF4` (20) |
| B5 | `KVM_ADAPT_BQ5` (25) | 100 % | `KVM_ADAPT_BF5` (15) |
| B6 | `KVM_ADAPT_Q_FLOOR` (20, the floor of every class) | 100 % | 15 |
| B7 | 20 | `KVM_ADAPT_SCALE_S1` (768 = 75 %; the lowest allowed is 70 %) | 30 |

Below B7 nothing more is lowered: the byte bucket (next paragraph) lets the motion frames out as often as the budget allows (a screen full of detail at 1 Mb/s: 1-2 frames per second). The scale steps 87.5 % and 70 % were measured and left out: only 75 % has the SSE2 scaler of the agent (3-5 ms for a 1920x1080 picture on a 2-core VM), 87.5 % and 70 % use the generic filter and cost 17-28 ms per picture, which limits the frames more than they save.

**The budget is a hard limit (byte bucket).** Every picture packet is paid from a bucket that is refilled at the budget rate (a burst of `KVM_ADAPT_BUCKET_BURST_MS` = 2 s, debt at most `KVM_ADAPT_BUCKET_DEBT_MS` = 3 s). A rectangle that is not small (more than `KVM_ADAPT_BUCKET_SMALL_TILES` = 8 tiles of 32x32) and finds the bucket empty is held back like a frame-limited one (the tiles are "deferred", looked at again in the next frames and sent when the bucket allows, in the quality of the step); small rectangles (typing, the cursor) pass while the debt is below one second of the budget. From step B3 on, every rectangle above 8 tiles is sent in the quality of the step even if its tiles are not "moving" (and sharpened later). `KVM_ADAPT_BUCKET_SHARPEN_PCT` (20 %) of the rate is reserved for sharpening, so that it always finishes; the part nobody uses goes to the motion. The ladder goes down when a window is above 110 % of the budget or when the bucket was empty for half of it (as many steps at once as the debt says, at most 3 per window; no second window needed when the debt is deep), up one step after 6 windows under the budget with a bucket that was almost never empty.

**Scale of the picture.** The agent keeps the scale the viewer asked for (command 5) apart from the share the budget asks for (`SCALING_FACTOR_NEW` = viewer scale x share, set in one place, `scale_update`). The viewer asks again after every change of the size of the picture; the same scale does not touch the share (neither does a viewer that sends back the scale it was given), another scale starts it again from 100 %. The scale changes only while the screen moves: at least `KVM_ADAPT_SCALE_DOWN_MS` (3 s) between changes down, `KVM_ADAPT_SCALE_UP_MS` (10 s) going up while moving, never within `KVM_ADAPT_SCALE_INPUT_MS` (1.5 s) of a mouse or keyboard command of the viewer (clicks around a change of the size would land beside), and not within `KVM_ADAPT_BUDGET_WARM_MS` after a REFRESH or a change of the scale (the full picture of a still screen is not movement). **Movement** means frames with at least `KVM_ADAPT_MOTION_TILES` (16) tiles that really changed (a caret, a clock, or a picture seen for the first time after a change of the size do not count). After `KVM_ADAPT_SCALE_RESTORE_MS` (3.5 s) without movement the picture goes back to the scale of the viewer at once, and the scale does not go down again for `KVM_ADAPT_SCALE_BAN_MS` (20 s; the bucket paces the frames meanwhile). The still picture is in the scale and quality of the viewer: it is sent in the quality of the step first and sharpened under the budget (a full 1920x1080 picture at 1 Mb/s takes about 12 s, at 100 kbit/s several minutes: sharpening always finishes, its reserved share keeps coming). At the end of a session the scale of the viewer is requested again. Log: `adapt scale mult=<1/1024> from=.. viewer_scale=.. step=B<n> calm=<0|1>`; `adapt stats` has `scale_mult`, `scale_changes`, `bucket_defers`, `bucket_tok_kb`, `bucket_forgiven_kb`.
*Held-back changes cannot starve, and the order is by age.* Every held-back tile carries the time it was first held back (`deferredAt`). Once the oldest has waited `KVM_ADAPT_BUCKET_AGE_MS` (1 s), held-back changes go out in the order of their age (a rectangle passes when it holds a tile held back no later than the oldest + `KVM_ADAPT_BUCKET_AGE_TOL_MS` = 100 ms), not in the order of the scan, which starts at the top left: without that, what keeps moving at the top of the screen was sent again and again before anything below it (measured: 1 Mb/s, heavy content on the whole screen, the centre of the screen refreshed 3 times in 35 s while the top refreshed 21 times). A new change waits behind the older ones and takes its place by its time. Small rectangles (up to `KVM_ADAPT_BUCKET_SMALL_TILES` = 8 tiles: typing, the cursor, small animations) have a reserved share of the rate (`KVM_ADAPT_BUCKET_SMALL_PCT`, 20 %; what they do not use goes to the motion) and do not wait in the queue of the large ones; the debt of that share is capped at half a second of it and what is above the cap is paid from the main bucket (every byte is accounted for: a flood of small detailed rectangles is limited to the budget as well; measured: 8 tiles of random pixels on every frame, 200 kb/s: 104 % and one window of 114 % before the change); a small rectangle passes on its share only while the debt of the main bucket is shallower than `KVM_ADAPT_BUCKET_SMALL_GATE_MS` (1 s of the budget); at a deeper debt (a flood of them) it is held back and takes its place in the queue by age like a large one, so a flood neither pushes the main bucket to its limit (bytes forgiven) nor starves the large ones. While changes are held back, sharpening has only its own reserved share (not the positive tokens of the main bucket). Under a budget a rectangle has at most `KVM_ADAPT_BUCKET_MAX_TILES` (64) tiles and no more than about half a second of the budget (by the size of the last ones; at least 4 tiles), so the bucket rations a large picture in pieces; the debt is capped at `KVM_ADAPT_BUCKET_DEBT_MS` and what the cap forgives is counted (`bucket_forgiven_kb`, 0 in all measurements). The burst of the bucket is `KVM_ADAPT_BUCKET_BURST_MS` (500 ms).
*Known limits of the scale.* (1) The viewer's echo of the scale it was given is recognised only within 5 s of the change; a viewer that deliberately chooses the scale the agent has just set within that time is taken for the echo (and later the agent returns to the previous scale of the viewer). (2) The scale can change while a mouse button is held without moving for more than 1.5 s (the release then lands beside); only mouse and key commands are tracked, not the state of the buttons.
*Known limits.* The fast scaler (SSE2) exists only for the result 75 % of the screen: with a viewer scale other than 100 % the multiplier 75 % gives another ratio and the generic filter (17-28 ms per 1920x1080 picture on a 2-core VM). Viewers other than the browser client, which send back a reduced scale as their own, were not tested (the agent ignores a command 5 whose scale equals the current result). The agent draws no cursor overlay at a scale other than 100 % (the browser draws its pointer), also when the budget has lowered the scale. Two viewers of one desktop share the scale and the budget (the last one wins).
*Known limits of very low budgets* (worked out from the code, not measured; the viewer's list starts at 1 Mbit/s). Worst case: 8 tiles of noise that change in every frame, about 30 KB a frame. (1) Below about 0.5 Mbit/s such an animation can take the whole budget: larger changes next to it wait as long as it runs, the limit is kept. (2) Below about 0.15 Mbit/s it can exceed the limit by a few to some ten percent, because bytes are forgiven at the debt floor of the bucket; `bucket_forgiven_kb` in the statistics shows them.

The budget is a second input next to the blocked-write time of WA-2: the motion quality is the lower of the two (`min(q of the congestion level, q of the budget step)`), the frame limit comes from the budget step (and the fixed limit below); the other effects of the congestion levels (frame pause, rate cap) are unchanged.
Down the ladder after `KVM_ADAPT_BUDGET_UP_WINDOWS` (2) windows above `KVM_ADAPT_BUDGET_UP_PCT` (110 %) of the budget; the first `KVM_ADAPT_BUDGET_WARM_MS` (3 s) of a session do not count (the full first image and its sharpening are not motion).
Back up one step after `KVM_ADAPT_BUDGET_DOWN_WINDOWS` (6, i.e. 3 s) windows below `KVM_ADAPT_BUDGET_DOWN_PCT` (100 %): the ladder tries the higher quality and falls back after two windows above 110 % if it does not fit (a try that fails soon doubles the patience, see below). The band 100-110 % is the hysteresis.
Version 1 of the ladder (down at 100 %, up only below 70 %) stayed on B2-B4 for a video whose steady output at B0 was 3.7-4.1 Mb/s, because the windows at the lower steps (3.0-3.4 Mb/s) never fell below 70 % of the budget.
A step that is given back and needed again within 10 s doubles the patience for the next recovery (6, 12, 24, 40 windows); after 30 s without a step back up (counted from the last return by one step) it is back at 6, so the quality does not oscillate. Sharpening of still tiles stays on (its bytes count in the window, the budget never switches it off);
typing, the cursor and small changes (not in the motion class) keep full quality and the loop pace.

**Who sets the budget.** The viewer chooses it (desktop settings: for example 10 Mb/s on a LAN, 4 Mb/s or less over a slow VPN). Precedence: value from the viewer > `MESH_KVM_BUDGET_KBPS` in the environment of the service (kbit/s, for tests) > `KVM_ADAPT_BUDGET_KBPS` (default 0 = no budget: without a viewer that sends the field the agent behaves as before WA-2b as far as the budget goes; the JPEG tables of mode 2 and the frame timer from 10 ms stay).
The log shows the source: `adapt start ... budget_kbps=<n> budget_source=<default|env|client>`, `adapt budget_set budget=<kbit/s> source=client` when the viewer changes it during a session, `budget_source` in `adapt stats`.
*Protocol.* Command 5 (`MNG_KVM_COMPRESSION`) has size 10: type (u8), quality (u8), scaling (u16), frame timer (u16), all after the 4-byte header. A viewer that offers a budget sends size **12**: bytes 10-11 = budget as u16, network byte order, in units of **100 kbit/s** (0 = no limit, 40 = 4 Mb/s, 100 = 10 Mb/s). `kvm.c` reads it with `if (size >= 12)` and calls `kvm_adapt_set_budget()` (a value written by the input thread, read by the loop at the next 500 ms window; the ladder restarts from B0; the same value again changes nothing). A command of size 10 (older viewer, thumbnails of several desktops) does not touch the budget.
Backward compatibility: older Windows agents and the Linux agent (not changed by this work; it reads `size >= 10` and ignores bytes 10-11) ignore the extra bytes. **The macOS agent rejects the whole command 5 when its size is not 6** (`mac_kvm.c`, `if (size != 6) break;`): that was already so for size 10, the new field does not change it. Only the Windows agent understands the field.
The budget of a viewer ends with its session (`kvm_adapt_session_end`): the next session in the same process starts from the environment / macro value unless its own viewer sends the field (a value that arrives between two sessions is kept for the next one). With two viewers of one desktop and no multiplexer in between, the budget of the last one that sent the field wins; thumbnails (size 10) never change it. The first 3 s of a session are not counted for the ladder, a REFRESH or a second viewer joining later is: a full picture can cost one step for a few seconds while the screen is still.

**Motion frame limit.** `KVM_ADAPT_MOTION_FPS` (default 0 = no fixed limit; `MESH_KVM_MOTION_FPS` overrides) and the limit of the ladder step; the stricter one applies. Rectangles of the motion class are encoded and written at most that many times per second (a frame may come up to half a loop period early, so that the average holds the limit);
rectangles of other classes go out in every frame. A held-back rectangle is not lost: its tiles keep the new CRC and get the flag `deferred`. The main loop looks at deferred tiles again in the next frame even if the capture does not list them as changed (`kvm.c`: the change map does not mark them "don't send"),
`kvm_adapt_want_image()` asks for an image while a deferred tile exists (like sharpening: the capture returns the unchanged persistent image with an empty change map when nothing new arrives), and the tile is sent in the motion class in the first frame the limit allows. A held-back frame counts as activity for the loop pace and the overlapped capture.

**JPEG tables.** `KVM_ADAPT_JPEG_OPT` (`MESH_KVM_JPEG_OPT`): 0 = standard Huffman tables, 1 = optimized tables (`TJPARAM_OPTIMIZE`, libjpeg-turbo 3.2.0) for the sharpening only, **2 = for every rectangle (default)**,
3 = sharpening and rectangles up to `KVM_ADAPT_JPEG_OPT_TILES` (16) tiles. Standard baseline JPEG, decoded by the browser unchanged. The gain comes mostly from the small rectangles of a moving picture: the standard tables cost about 420 bytes of header in every file.
Measured in the agent (Windows 10 VM, 2 cores, no budget, 60 s, frame timer 30 ms; mode 1 / 2 / 3): video 811 / 455 (-44 %) / 735 KiB/s at 31.8 pictures/s in all three, CPU of the KVM child 17.9 / 23.6 / 17.4 %, encode time per 32x32 tile 2 / 4 / 2 us;
scroll (text) 233 / 207 (-11 %) / 216 KiB/s at 26.7 pictures/s, encode time per tile 6 / 13 / 7 us. Host micro test (libjpeg-turbo, real frames): -42..-54 % for a 32x32 rectangle, -35..-52 % at 256x128 and -3..-47 % for the whole picture, encode time +3..+150 %; see the report.

**A frame without changed tiles** (the capture was asked for an image only to look again at held-back or lossy tiles) keeps the motion count of the last frame that changed something. Without that, the frame after it was taken for "no motion" and a moving picture was sent in full quality (q80, 4:4:4) for a moment.

**Frame timer.** The agent accepts a frame timer from 10 ms (was 20 ms) in both places of `kvm.c` (compression command and frame-rate command); only the Windows agent, Linux and macOS are unchanged.

**Stale check.** `dxgi stale_suspect|stale px=<n> box=<x0>,<y0>,<x1>,<y1>`: the rectangle around the differing pixels (x1, y1 exclusive, screen pixels, top-down); the check itself is unchanged.

**Log.** `adapt start` has `budget_kbps motion_fps jpeg_opt`; `adapt budget from=B<n> to=B<n> window_kbps budget_kbps q_motion fps_cap calm_windows since_start_ms` at every step; `adapt stats` has, appended:
`budget_kbps win_kbps_avg win_kbps_max bstep_end bstep_max bsteps q_motion_min q_motion_avg motion_fps_cap deferred_tiles deferred_rects enc_rects enc_us_rect enc_us_tile sharp_enc_rects sharp_enc_us_rect sharp_enc_us_tile loop_n loop_wait_us loop_proc_us loop_pause_us`
(`enc_*`: encode time of the rectangles of a frame, `sharp_enc_*`: of the sharpening; `_tile` = per 32x32 tile of the rectangle; `loop_*`: per iteration of the main loop, microseconds waiting for the capture, processing the frame and pausing).

## 8. End-to-end ACK of the viewer

The viewer tells the agent how far it has consumed the stream, so the agent can size its output to what the whole path (pipe, relay, multiplexer, network, browser) takes, not only to what the pipe takes (the signal of WA-2, which saw a 15-16 s lag at 3 Mb/s). The protocol is the commands 240-243 of `docs/kvm-dev/h264-protocol.md` in the MeshCentral fork (chapters 3, 4, 5 and 8). This package is the agent side with the JPEG picture only: there is no video encoder yet, and a viewer that asks for video is told "no video in this build" (242 reason 1) and still gets the ACK window.

Code: `meshcore/KVM/common/kvm_stream.{c,h}` (portable C99, no OS API, time injected; the protocol, the state of chapter 5 and the window; tests in `meshcore/KVM/common/tests/`, `run-kvm-stream-tests.sh` runs them in Docker with `-Wall -Wextra -Werror` and then with ASan + UBSan) and the glue in `kvm.c` (search "end-to-end ACK (commands 240-243)"). Active in the x64 `MeshService` build next to WA-2 (`KVM_STREAM_ENABLED` = `KVM_ADAPT_ENABLED` and not `KVM_STREAM_DISABLE`); in the other builds the agent eats 240 and 241 like before and never sends 242. `MeshService-2022.vcxproj` compiles `kvm_stream.c` for x64 only.

**Commands.** *240 VIDEO_CTRL* (viewer, multiplexer, meshcore -> agent, 16 bytes): op 1 video on (+ACK), 2 video off, 3 repair, 4 ACK only, 5 veto, 6 end of veto. *241 STREAM_ACK* (viewer -> agent): `seq`, `ts` of the last consumed position, `queueMs`, flags. *242 VIDEO_STATE* (agent -> viewer): `video`, `ack`, `reason`, caps (bit 1 = ACK), `gen`. *243 VIDEO_FRAME* inside MNG_JUMBO: in this build only the **marker** (28 bytes: `seq`, `ts`, flag MARKER, no rectangles), the "position" that the viewer acknowledges. Anything that does not pass the strict checks of 4.1 is dropped and counted (`input_bad`); a 240 or 241 whose size field is not 16 is dropped and the bytes it says it has are consumed, like for every other command of the stdin stream (never a guessed 16: the reads of the pipe can cut the stream anywhere, `kvm_stream_stdin_consume` is tested with streams cut at every position). **Bad size field on the stdin (any command, every build; `kvm_stdin.h`).** A size below 4 (the command is shorter than its header) is not a command: exactly its 4 header bytes are consumed, nothing is dispatched, `input_bad` counts it, and the parser goes on with the bytes behind the header. A size above the input buffer (30000, it can never be completed) is not a command either: the header and then the WHOLE declared length are thrown away (a counter of bytes still to discard, `kvm_stdin_parser`, holds across reads of any size), never read as commands, because meshcore passes such a frame on as one unknown command and a body read as commands would let a viewer smuggle a 240 op 5 / op 6 past its filter (meshcore must not pass such a frame at all). The parent's `kvm_veto_track` applies the same rule (header only below 4, `skip = size - 4` otherwise), so both stay at the same position. Before, size 0 stopped the parser for good (the buffer filled up and the session was closed), size 1-3 moved it into the middle of a header, and a size above the buffer waited the same way (the session was closed). The input buffer also moves the incomplete command to its start after every read (`kvm_stdin_compact`), which closes the same way out for a stream that always ends in the middle of a command. Commands that read bytes 4-5 (frame rate timer) or byte 4 and up (touch) now check their size first.

**Threads.** The input thread only validates 240 / 241 and hands them over: the 240 to the **inbox** (`kvm_inbox`), the 241 to a queue of 128 (a full ACK queue drops the oldest, an ACK covers the older ones; each item carries the time it arrived, the round trip is measured from that). The inbox cannot lose a command for lack of room (it replaced a queue of 32 that refused what came after it, so a flood of op 3 could push out the op 5 that meshcore sends when a second viewer joins): the veto is a state (`vetoTarget`, the sources after all op 5 / op 6 so far, plus `vetoPulse`, the sources set since the last iteration, so that a set followed by a clear still stops the video) and the main loop makes the veto of the stream equal to it before it looks at any other command; op 1 / 2 / 4 keep only the last (it is what the viewer wants now), op 3 flags are ORed into one repair; ordinary commands (op 1-4) pass a token bucket (40 per second, burst 32, `KVM_INBOX_RATE` / `KVM_INBOX_BURST`) and the rest is dropped and counted (`ctl_dropped`; `ctl_merged` counts the commands that replaced or joined a waiting one); the veto does not pass the bucket. Per iteration the main loop handles at most four commands: op 5, op 6, the request, the repair. The main loop handles the queues at the start of every iteration (`kvm_stream_poll`), then the timers; the answer (242) is written before the next picture. Every write of the process (tiles, cmd 7, cursor, display list, 242, markers, also what the input thread writes for a REFRESH) goes through one write function under one lock (`kvm_child_write`), which counts the bytes; the byte count and the ring of positions therefore describe the same order. In console mode (no child process) the same happens in the agent process.

**Window.** The agent remembers the last 1024 positions `{seq, ts, bytes written}` (a full ring overwrites the oldest). An ACK counts only when `(seq, ts)` is in the ring and newer than the last accepted one (a forged, repeated, late or overwritten one is ignored and counted), and at most 200 per second (token bucket, burst 50) before the ring is searched. `inflight` = bytes written - bytes covered by the last accepted ACK. `rate` = the largest of the delivery rates over at least 500 ms in the last 2 s (a sample from a time when the sender was never held back by the window only raises the rate, as in K2); `minRtt` = the smallest `now - ts - queueMs` of the last 10 s (at least 1 ms; see "Round trip" below); **W = clamp(rate x (minRtt + 200 ms), 64 KiB, 4 MiB)**, 256 KiB before the first rate sample of an activation. When there is no sample in the last 2 s (a pause in the traffic) the last measured rate is kept, so W does not go back to 256 KiB after a pause; only missing ACKs with data in flight lower it (the 2 s rule below). Gates, checked before the write: a JPEG rectangle of more than 8 tiles needs `inflight < W`, a rectangle of up to 8 tiles `inflight < 1.25 W`, sharpening `inflight < 0.5 W`. They are applied in WA-2 where the byte bucket of WA-2b is: a refused rectangle is "deferred" (looked at again in the next frames, `kvm_adapt_bucket_closed`), sharpening gets no budget (`kvm_adapt_sharpen_budget`), and the capture is not hurried while the window is full (`kvm_adapt_want_image`). The WA-2 regulator (blocked pipe write, budget ladder) stays as the second signal.

**Round trip.** The first picture of a session is still in the pipe when the viewer asks for ACK, so the first positions wait behind it. Nothing is measured until the pipe has been empty once (an ACK that leaves nothing in flight); only positions written after that count. `minRtt` is the minimum of the last `KVM_STREAM_RTT_WINDOW_MS` (10 s). A queue that never drains (a window that is always full) would keep a queue-inflated `minRtt`, so an **RTT probe** (`ProbeRTT-lite`) refreshes it: when the value is older than 10 s, the window refused a write in the last second, and no probe ran in the last `KVM_STREAM_PROBE_INTERVAL_MS` (10 s), the gates close at the start of an iteration (a picture is not cut: the decision is made there, the refusals are per rectangle, and what is refused is deferred, not lost), the data in flight drains, and the marker that goes into the empty pipe gives a clean round trip, which replaces `minRtt`. The probe is given up after the expected drain time plus max(200 ms, `minRtt`) (`KVM_STREAM_PROBE_MIN_MS`), and its marker is waited for 3 s. Log: `rtt_probes=<started>/<done>/<given up>`.

**Markers (rule M1).** Every iteration that wrote bytes other than a marker or a 242 ends with a marker, so every byte written is behind a position the viewer can acknowledge; without it the window could stay closed for ever. **Probe marker (M2):** with data in flight and no ACK for 1 s (and not more than once a second) a marker is written even if the loop wrote nothing: its ACK also releases the bytes that the multiplexer dropped on overflow, which would otherwise keep `inflight` above W for good.

**Timers.** No ACK for 2 s with data in flight: W = 64 KiB until the next ACK. No ACK for 15 s: ACK is off and the agent sends 242 reason 9 (the viewer asks again); the writes are no longer limited. Time without data in flight never counts. A blocked write (`g_pause`, or a write that took more than 100 ms) stops the clocks. "Pause" for these timers is only that: the flag `g_remotepause` (command 8) is written but read by nobody in the Windows agent, and 242 and markers never depend on it.

**Veto (two or more live viewers).** Op 5 / op 6 carry the source in `flags` (bit 0 meshcore, bit 1 multiplexer); the agent keeps the mask (only the bits 0 and 1 exist: `KVM_VETO_ALL`; reserved bits of the flags are ignored, never stored in the stream, the inbox or the parent's tracker, so they cannot be handed to a new child), `veto = mask != 0`, so the end of one source does not lift the other. While veto holds, the agent answers op 1 / 2 / 4 with 242 reason 5, ACK is off and nothing is limited; when the mask becomes 0 the agent answers reason 10 and the viewer has to ask again. The parent process (`kvm_relay_*`) follows op 5 / 6 on their way to the child (`kvm_veto_track` frames the stream by the size fields across writes, so a command cut between two writes is seen whole) and gives the remembered mask to every new child (UAC, lock screen) as an op 5 before any other input; it starts empty with a new session and is cleared by `kvm_cleanup`.

**242.** At the start of the process (also a new child): reason 11, no video, no ACK, caps = ACK. Reasons used here: 0 (op 2 / op 4 done, op 6 with nothing to lift), 1 (op 1: no video in this build; ACK is on), 5, 6 (ACK switched off, see below), 9, 10, 11. Op 3 is never answered (it is ignored without video). Every 242 carries the current `gen` (0 until there is video) and `caps`.

**Switches.** `/DKVM_STREAM_DISABLE` (compile time; workflow input `extra_cl`): the build without the layer. `MESH_KVM_ACK=0` and `MESH_KVM_ADAPT=0` (environment of the service, as for WA-2): the layer is compiled in but ACK is not offered: caps = 0, op 1 / op 4 are answered with reason 6, nothing is limited. The same happens while the picture type is not JPEG / WebP (command 5): ACK goes off with 242 reason 6 and comes back with reason 10 (the viewer asks again). Only `/DKVM_STREAM_DISABLE` (and the x86 / ARM64 builds) gives the byte stream of an agent from before 240-243, without any 242. Constants (`KVM_STREAM_*` in `kvm_stream.h`: W start / min / max, queue delay 200 ms, rate span 2 s / 500 ms, gate percents, stall 2 s, timeout 15 s, probe 1 s, ACK rate 200/s and burst 50, ring 1024) can be overridden with `/D<NAME>=<value>`.

**Log** (with the statistics log of section 5 on): `stream start cap_ack=..`, `stream ctrl op=.. flags=..`, `stream state video=.. ack=.. reason=.. caps=.. gen=.. veto=..` at every 242, and once per statistics period `stream stats ack want veto win_kb inflight_kb rate_kbps min_rtt_ms acks_ok acks_off acks_flood acks_unknown acks_stale markers probes stalls timeouts gate_denied ctrl_ok input_bad ctl_dropped ctl_merged ack_dropped`.

**Known limits.** (1) Until the first RTT sample (the pipe has to be empty once, or the first probe 10 s after the activation) `minRtt` is 0 and W = rate x 200 ms (at least 64 KiB): on a link with a round trip above 200 ms under constant load the window starts small and grows by the rate it measures (a factor of about 1 + 200 ms / RTT per round trip) until the probe or a drained pipe gives the round trip. (2) There is one position per iteration: a picture of several hundred KB written in one iteration is acknowledged as a whole, and W bounds it (the gate looks at `inflight` before each rectangle, not at the size of the rectangle). (3) Command 6 (REFRESH) and cmd 7 written by the input thread are counted and covered by the next marker of the main loop. (4) A viewer that sends no ACK (an old page) never switches the window on: `want` stays NONE.

**Tests.** `meshcore/KVM/common/tests/run-kvm-stream-tests.sh` (Docker, gcc): all 62 vectors of `vectors.json` (generated into `kvm_stream_vectors.h` by `gen_stream_vectors.py`, which names the SHA-256 of the source), the generators (256 and 257 rectangles, N = 8 MiB and 8 MiB + 1, seq wrap and gap), build = inverse of parse for every valid vector, every prefix of every vector under ASan, the state machine (veto mask, restart, switched-off ACK, build with video), the ring (overwrite, forged, repeated and late ACK, seq wrap, 200/s limit), the gates and their edges, an IDR larger than W with nothing in flight, the two deadlocks (the multiplexer drops bytes: the probe marker reopens the window; the viewer is gone: 2 s, 15 s, 242 reason 9), pause, a blocked write, a simulated link at 40 / 10 / 0.5 Mb/s (W follows the rate), rule M1 as a property over 20 000 random iterations, and the same scenarios with the millisecond counter wrapping. Also tested: the inbox (op 5 after 1000 x op 3 and op 6 after a flood are applied by the next iteration, set then clear in one iteration, joining of op 1 / 2 / 4 and op 3, the token bucket and its wrap), bad size fields 0, 1, 2, 3, 30001, 40000, 65535 at the head of a stream cut at every position, oversized frames with a valid 240 op 5 / op 6 / op 1 inside the body (reads of 1, 7, 4096, 30000 bytes and cuts at the header and the end of the body: none is dispatched, the child's veto and the parent's tracker agree), 800 kB of zeros and a stream that always ends in a half command (no 0 byte read), every value of the veto flags (reserved bits never kept); `run-kvm-stream-mutations.sh` (36 mutations of these rules, all killed). ## 9. H.264 video path

Motion in the picture (scrolling, video, a window that is dragged) is not sent as JPEG tiles but as H.264 frames; the tiles that moved are painted by the frames, and WA-2 sharpens them as JPEG when the motion stops. Typing and small changes stay JPEG. The picture stays JPEG-based: the viewer paints H.264 only inside the rectangles of a frame, and the agent sharpens every such tile afterwards, so a still screen is the same as without video. The protocol is the commands 240-243 (`docs/kvm-dev/h264-protocol.md` of the MeshCentral fork, chapters 3, 5, 8, 9); the QP regulator and the bandwidth target are not here: the quantizer is fixed (28, never below 26, `KVM_VIDEO_QP`, `KVM_VIDEO_QP_MIN`).

Code: `common/kvm_video_core.{c,h}` (portable C99, no OS API: the tile bookkeeping, the rectangles of a frame, level and profile, the controller of chapter 5.2/5.3; tested in Docker), `Windows/kvm_video.{cpp,h}` (the glue: encoder, tiles, pipe, log), `Windows/mf_h264.cpp` (the encoder), `common/kvm_yuv.c` (BGRA to NV12), `common/kvm_annexb.c` (Annex B clean-up), `kvm_stream.c` (the 243 builder, now also in two parts: header, then the data encoded straight behind it), hooks in `tile.cpp` (`get_tile_at`), `kvm_adapt.cpp` (sharpening, `sentQ`), `kvm.c` (the loop, the glue of the lock). `MeshService-2022.vcxproj` compiles them for x64 only; Media Foundation is loaded with `LoadLibrary` (mfplat.dll, ole32.dll): **no new import** (to be checked with `dumpbin /imports MeshService64.exe` against 19ef851). `KVM_VIDEO_ENABLED` = `KVM_STREAM_ENABLED` and not `KVM_VIDEO_DISABLE`; x86 / ARM64 and `/DKVM_STREAM_DISABLE` have none of it. `agentcore.c` sets the JS property `kvmVideoProtocol = 1` on the desktop stream (`getRemoteDesktopStream`) in the builds with the stream layer; without it `agents/meshcore.js` keeps the old input path (`pipe(kvm)`) and does not send op 5/6.

**States (5.2).** The viewer's request (op 1) is `want = VIDEO` in the stream layer; the video code then starts a generation: the encoder is created for the coded size (screen padded to 32), the profile is the highest the viewer's flags allow (High, Main, Constrained Baseline; one down when the encoder refuses a profile, reason 8 when none is accepted), the level is the smallest for 60 frames per second (`kvm_vcore_pick_level`; 30 frames per second and a frame rate cap when the viewer's `maxLevelIdc` needs it; reason 7 above, also for a size over `maxW`/`maxH` and for the encoder's refusal of the size), `gen++` and a 242 (video 1, ack 1, profile and level **from the SPS the encoder wrote**, coded size, gen) before anything of the new generation, then the first frame is an IDR. Reasons: 2 no Windows 8 / Media Foundation / encoder (`caps` bit 0 = 0), 3 the encoder did not start, 6 `MESH_KVM_VIDEO=0`, `/DKVM_VIDEO_DISABLE`, `MESH_KVM_ADAPT=0`, 7, 8 as above. Op 2, op 4, veto, no ACK for 15 s and a picture type other than JPEG / WebP switch the video off (the stream layer answers; the encoder is released, the pending tiles go back to JPEG). A new size (cmd 7) starts a new generation (a new encoder when the coded size changed). The encoder is created at most once in 2 s (the tiles go as JPEG meanwhile); op 1 within 2 s of an accepted one is joined with it (the answer is the current state).

**Errors.** A failed call of the encoder, a frame over 8 MiB, three lost access units in a row, or a first frame that is not an IDR three times: the video is off (242 reason 4, `want` stays VIDEO), the pending tiles go as JPEG, and after 60 s the same request is made again (new generation); the third error is for good (`caps` bit 0 = 0, op 1 gets reason 6). One lost access unit (`MFH264_E_STREAM_BROKEN`: the wrapper flushed the encoder) is not an error: the frame is not sent, the tiles stay pending, the next frame is an IDR at once. A structured exception in any call (guarded in `mf_h264.cpp`) switches the video off for the process without closing the encoder or shutting Media Foundation down (they are leaked on purpose).

**Tiles.** A rectangle of the motion class (`kvm_adapt_class`; tiles of a REFRESH or a repair are never video) that `get_tile_at` has coalesced is not encoded as JPEG: its tiles are `PENDING` (`kvm_video_claim_rect`, `pendingVideo`). A tile is in exactly one place: JPEG sent (`kvm_adapt_sent` and the sharpening call `kvm_video_tile_jpeg`: it leaves pendingVideo and VIDEO), PENDING, or VIDEO. At the end of an iteration with pending tiles (`kvm_video_emit`, after the tile loop, before the sharpening) one frame paints the **sum of the pending tiles since the last frame**: the rectangles (at most 256, tile aligned, inside the screen, neighbours merged into bounding boxes when there are more) cover them, and every tile inside a rectangle becomes VIDEO, also tiles that were unchanged or were sent as JPEG in the same iteration: `lastChange = now`, `crc = contentCrc` (kept 0xFF if a REFRESH came meanwhile), `sentQ = 1`, `sentSub = 1` (below every quality of the user), so WA-2 sharpens them 150 ms after the motion stopped. Sharpening skips pending tiles. Video off: the pending tiles get `crc = 0xFF` and the next captured frame is full, so they go as JPEG; the VIDEO tiles are sharpened as usual. Op 3 repair (and op 1) gives the VIDEO tiles `crc = 0xFF` the same way (at most once a second, requests are joined); a REFRESH clears the model. A tile that changes again in the full class (typing) is sent as JPEG and leaves the pending set.

**Sharpening must not starve.** While the video runs, a tile that has been due for `KVM_VIDEO_SHARPEN_WAIT_MS` (1 s) without any sharpening by the normal budget is sharpened anyway: at most `KVM_VIDEO_SHARPEN_FORCE_BYTES` (16 KiB) every `KVM_VIDEO_SHARPEN_FORCE_MS` (250 ms), regardless of the window, the byte bucket and the token limit. Counted in `adapt sharpen_forced=`. The 75 % step of the budget ladder is not used while the video runs.

**Frames (243).** Always inside MNG_JUMBO. A frame is a position (rule M1): `seq` and `ts` come from the ring under the lock, the Annex B data is encoded straight behind the header (`kvm_stream_build_frame_header`). The window gate is `inflight < W` before the encoder is called (an IDR bigger than W passes when `inflight < W`, so always at zero); a refused frame is "held back": the pending tiles keep accumulating and the next frame is bigger (that is the "less fps"); an encoded frame is never dropped. The pace is the frame timer of the viewer (not below 16 ms, not below the cap of the level), stretched to the budget of the encoder (chapter 12); a frame may come 25 % early. **Lazy IDR:** nothing is encoded without pending tiles, not even a key frame that was asked for. IDRs: the first of a generation is never delayed (a reused encoder gets `AVEncVideoForceKeyFrame`; if the first frame of a generation is not an IDR it is not sent and an IDR is forced); op 3 / the key frames of a recording (flags 1) wait for `max(1 s, 2 x IDR bytes / rate)`, at most 10 s (`KVM_VIDEO_IDR_MAX_MS`, not in the specification), requests are joined. The bytes of a frame go to the WA-2 regulator and byte bucket (`kvm_adapt_note_write`); the bucket holds back only JPEG.

**Fixes (second round).** The SPS of the encoder is checked against the viewer's request before anything is sent (`kvm_vcore_check_sps`, `kvm_annexb_sps_info`): at open from the sequence header (`mfh264_seq_header`), and again on every IDR; profile not in the flags, Baseline without constraint_set1, more than one reference frame (the encoder is also asked for `AVEncVideoMaxNumRefFrame = 1`), not 4:2:0 8 bit, frame cropping -> 242 reason 8 or 7 (level above the viewer's, more than 36 864 macroblocks, other size) and JPEG. When the picture type leaves JPEG / WebP (or the colour depth changes) the VIDEO tiles go back to JPEG like the pending ones. Forced sharpening is at most 20 % of the delivery rate (packets of 4-16 KiB, the interval grows when the rate is low) and not while `inflight >= 2 W`. The frame interval is at least twice the average encode time (at most 250 ms); a picture is ordered only when a frame may go. The scale of the picture does not change while a generation runs or waits for its encoder. An op 1 is joined with the previous one only while that start succeeded or is under way; its limits are always remembered (also in the hold-off after an error). The statistics log is renamed to `<name>.1` at 1 MiB and restarted (two files, at most about 2 MiB), so it never silently stops. A further fix (the check of `crc != 0xFF` in `tiles_painted` is not atomic against a REFRESH of the input thread): the effect corrects itself, the tile is blurred and will be sharpened; the JPEG path has the same pattern.

**Log** (statistics log on): `video init ok ms=` / `video init failed`, `video start cap_video= reason=`, `video encoder open size= profile_asked= level_asked= sps_profile= sps_level= level_set= max_au_kb= ms=`, `video start kind=<1 op 1, 2 new size, 3 retry> gen= profile= level= coded= fps_cap= qp= fresh=`, `video request failed reason=`, `video stop why=`, `video error what= code= hr= stage= exc= errors=` + `video off retry= cap_video=`, `video lost access unit`, `video repair tiles=`, `video sps differs from the 242`, and once per period (quiet while nobody uses the video) `video stats state= cap_video= frames= idr= idr_kb= forced_idr= kb= enc_ms_avg= enc_ms_max= write_ms_avg= rects_avg= claimed_tiles= held= pace_skips= lost_au= errors= fallback_tiles= sps_mismatch= pending= pending_max= video_tiles= qp= fps_cap= repairs=`.

**Switches.** `/DKVM_VIDEO_DISABLE` (compile time) and `MESH_KVM_VIDEO=0` (environment of the service): the stream layer stays, op 1 gets 242 reason 6, the picture is JPEG. Constants (`KVM_VIDEO_*` in `kvm_video_core.h` and `kvm_adapt.h`) can be overridden with `/D<NAME>=<value>`.

**Tests** (Docker, gcc, no machine): `common/tests/run-kvm-video-core-tests.sh` (plain `-Wall -Wextra -Werror -pedantic`, then ASan + UBSan; also re-runs `kvm_stream_test`): the bytes of a 243 and its limits (256 / 257 rectangles, N = 8 MiB / + 1), the rectangles (shapes, clipping to a 1366x768 screen, a chess board of 1020 tiles, exactly 256 and 257 rectangles, a property test over 300 patterns and 7 screen sizes), the tile model against an independent model over 24 000 random events, levels and profiles, the IDR spacing, op 1 joining and the 2 s limit, the error policy and its time wrap, the plan of a frame (lazy, window, pace, IDR rules, lost access units), repair rate, and a random whole-session property (a 242 for generation N before every frame of N, the first frame of a generation is an IDR, seq +1). `run-kvm-video-mutations.sh` changes 24 key rules in copies of the code, one by one, and requires the tests to fail (24 of 24). `Windows/tests/run-kvm-video-harness.sh` compiles the production `kvm_video.cpp` on Linux (g++; a shim of `<windows.h>` with a fake clock, the real core and stream modules, a **fake encoder**, a fake glue that records every write, fake `tileInfo`) and drives it as `kvm.c` does: op 1 and the 242 with the SPS profile and level, the first frame (IDR, rectangles, tile marks), pace and window, op 2 / op 4 / veto, lost access units, a first frame that is not an IDR, the third error, a structured exception, refusals (reasons 2, 3, 7, 8), a new size and its 2 s limit, repair, REFRESH, op 3 IDR spacing, a chess board of 1020 tiles, write results (3661 checks, also under ASan + UBSan); `run-kvm-video-harness-mutations.sh` breaks 19 rules of the glue one by one (19 of 19 caught). ## 10. Rate control of the video

Code: `common/kvm_video_rc.{c,h}` (portable, tested in Docker with a link simulation: `common/tests/run-kvm-video-rc-tests.sh`, mutations `run-kvm-video-rc-mutations.sh`), glue in `kvm_video.cpp`. Spec 8.5.

- **Target R** = min(0.8 x the viewer's budget (command 5, `kvm_adapt_viewer_budget_kbps`), capacity estimate); 2 Mb/s while neither is known; never below 100 kb/s. The capacity estimate is 0.85 x the delivery rate of the ACK window *only while the link is the limit*: the window refused a video frame or a big JPEG rectangle in the last second (`kvm_stream_link_limited`, raised by `kvm_stream_note_link_held`; the sharpening gate of 0.5 W and the closed gates of the RTT probe only feed the rate samples, `kvm_stream_note_held_back`; without it R shrank 3492 -> 2769 kb/s at 5 Mb/s). Otherwise the rate only says what was sent (the video is held by its own bucket), so the estimate does not fall; it grows by 25 % per second only while the bucket refuses frames *and the estimate itself, not the budget, is R*, and never above 2 x max(0.85 x rate, 2 Mb/s) (with a budget below the link it ran away, and overflowed after about 100 s). The literal "0.85 x rate" of 8.5 would make R decay by itself (R limits the sending, the sending sets the rate); the simulation showed it.
- **Byte bucket** (R bytes per second, burst 0.5 s, debt at most 2 s): a frame is encoded only while the bucket holds something; its bytes are debited. The long run never exceeds R; at the QP ceiling the frame rate is whatever R allows (the encoder is asked less often, `pendingVideo` accumulates, an encoded frame is never dropped). The first frame of a generation and a key frame after a lost access unit are not refused. The WA-2b byte bucket of the JPEG path counts the video bytes (`kvm_adapt_note_write`) but holds back only JPEG.
- **QP regulator** every 500 ms on the P frames of the window (IDR frames are not counted): above 110 % of R, or frames were refused and the stream is above 90 % of R: QP + 2 (ceiling 38); below 70 % with at least 3 frames and no refusal of the bucket for two windows in a row, or below 80 % when neither the bucket nor the window of the viewer refused anything in the window (the encode time limits the frames, so 70 % never comes on a fast link: noise at 50 Mb/s sat at QP 38 with the video at 0.79 R, now 37 and 0.88 R): QP - 1 (floor 26). Per window and not per frame: the window is the unit of the specification and of the byte counters, a frame has 3.6-250 KB and a single one says nothing; the hysteresis (two quiet windows) keeps a step down (the next frame about 20 % bigger) from oscillating. After 10 s without a frame the QP goes back to 30 if it was above (a still screen says nothing about what the next motion costs, and a step down takes a second). IDR frames get max(QP - 4, QP_link), clamped to 22..38 (`mfh264_set_qp` before the frame, only when the value changes): QP_link is the smallest QP at which the predicted key frame (the last one measured, before the first one 200 KB at QP 28 for 1920x1088 scaled by the pixels; 6 % per QP) fits in 0.75 s of R. The range is wider than 22..32 because at 1 Mb/s and below a 1080p key frame is only that small at the top of the P range (about 90 KB at QP 38); the key frame at 30 s takes 0.9-1.3 s at 1 Mb/s and 2.1-2.9 s at 0.5 Mb/s in the simulation (4.8 s before), the first one is encoded before the rate is known. Forced sharpening takes its 20 % of min(rate, budget).
- **Encode cap**: the frame interval is at least encode time x cores busy while it encodes / the CPU budget of the encoder, see chapter 12; fewer frames rather than a stalled capture, JPEG and input. IDR spacing uses the remembered rate (`rate_or_mem`).
- **Log** (statistics log, every second while the video runs): `video rc r_kbps rate_kbps budget_kbps link_limited starved qp qp_idr fps idr video_kb sharpen_kb enc_ms_avg enc_ms_max interval_ms denied win_refused qp_up qp_down bucket_kb`. `starved=1` when the QP is at the ceiling, fewer than 2 frames a second are made and the bucket or the window of the viewer refuses, for 5 s (only a flag, no protocol field, no way back to JPEG). `video stats` gets `held_rate`.
- Also: the scale ladder may not step down while the video runs or waits for its encoder, but may return to the viewer's scale 10 s after the last generation began (`kvm_vcore_scale_allowed`); VIDEO tiles go back to JPEG when the sharpening path disappears even after the video was switched off; an op 1 joined with a running start does not change the limits in force (they apply from the next generation); a failed rename of the full statistics log empties it instead.

## 12. Frame rate: the schedule of the loop and the CPU budget of the encoder

Code: `common/kvm_pace.{c,h}` (portable, tested in Docker with a simulation of the loop: `common/tests/run-kvm-pace-tests.sh`, mutations `run-kvm-pace-mutations.sh`), glue in `kvm.c` (the loop, the `pace` line) and `kvm_video.cpp` (`frame_period_ms`, `frame_interval_ms`, `kvm_video_wake_ms`, the `video pace` line).

- **The viewer's period is the period.** The viewer's list is High 16 ms (60 per second), Medium 33 (30, default), Low 50 (20), Slow 100 (10), for JPEG and H.264 alike (commands 5 and 6 / `FRAME_RATE_TIMER`). The video no longer inherits 50 ms: its interval is that period, not below 16 ms (`KVM_VIDEO_MAX_FPS` 60) and not below the cap of the level of the stream. Older viewers (20 / 50 / 100 ms) behave as before. Where the old floor was: `KVM_ADAPT_MIN_FRAME_TIMER` (`kvm_adapt.h`), used in `kvm.c` for command 5 (size >= 10, bytes 8-9) and command 6; it was **10** in the x64 build with WA-2 (`KVM_ADAPT_ENABLED`: TurboJPEG, stats log, no `/DKVM_ADAPT_DISABLE`) and **20** in every other build (x86, ARM64, x64 without TurboJPEG), where a request below 20 ms was ignored (the timer stayed what it was). It is now 16 in those builds; the Linux agent (`linux_kvm.c`, `fr >= 20`) and macOS are unchanged. A viewer that sends 20 and then 16 ends at 16 where 16 is accepted and at 20 where it is not.
- **The loop is on a schedule** (`kvm_tick`): the next iteration starts one period after the slot of this one, not one period after this one began. A wake that is 1 ms late every time no longer costs 1 ms per frame (6 % at 16 ms); an iteration that overran its slot starts the next at once, the debt is paid back within a period, a debt of a whole period is forgotten (no burst of catch-up frames); an idle loop (nothing sent, or the capture waited for changes) has no schedule.
- **A video frame has a slot** (`kvm_pace_slot`): the slot is the previous slot + the interval, not the moment the previous frame was written, so the rate holds the interval. While a frame waits only for its slot (pending tiles, the window of the ACK and the byte bucket open) the loop wakes for it (`kvm_video_wake_ms`) when it comes before the next iteration of the schedule; it never sleeps longer than its own period (the 240 / 241, a REFRESH and the JPEG of a typing echo are looked at as often as before). That removes the aliasing of a loop whose period is a little less than the interval (a frame on every second iteration: 16.7 frames per second for a 30 ms timer and 25 ms encoding).
- **CPU budget of the encoder** (decision of the design): at most 50 % of the machine (`GetSystemInfo`, logical processors of the group), not less than one core (50 % is one core from two processors up; on one processor the encoder keeps to half a core, so it never takes the whole machine). The encoder works on slices in parallel, so an encode call of `e` ms of wall time uses `e x p` ms of CPU; `p` is measured (the CPU time of the process during the encode calls, `GetProcessTimes`, over their wall time, a moving average over windows of 500 ms, clamped to 1.0 .. min(cores, 8); 1.5 until measured). The interval is at least `e x p / budget`: one core and p = 1 let the encoder run all the time, p = 1.5 on two cores makes 67 % of the loop. It replaces "twice the encode time". The bandwidth regulator (chapter 10) is unchanged and limits the frame rate on its own account. The CPU of the whole process is reported, not regulated. The CPU time of the capture thread (`GetThreadTimes`), which captures the next frame beside the encoder, is subtracted; what is left is the encoder and its worker threads (the input thread is negligible). Without a readable capture clock `p` is a little high (safe side).
- **A new child process** (UAC, lock screen, a change of desktop) starts with the defaults of the agent, and the viewer does not repeat its settings. The parent (`kvm_veto_track`, `kvm_veto_replay`) remembers the last command 5 (quality, scale, frame timer, budget) and the last command 13 and gives them to the new child after the veto; the default frame timer of a child is 33 ms (was 50). Only where the stream layer is built (x64 with WA-2); elsewhere the default of 33 ms alone.
- **Imports.** Three new KERNEL32 imports in the KVM code: `GetProcessTimes`, `GetThreadTimes`, `GetSystemInfo` (the DLL is imported already).
- **Log.** `pace` line with every statistics line: `viewer_timer_ms cores cpu_ms cpu_cores cpu_pct_machine fps_jpeg fps_video dwm_images dwm_frames dwm_per_image_avg dwm_per_image_max dwm_fps tick_n tick_late tick_late_ms_avg tick_late_ms_max tick_over tick_resync` (`dwm_*`: `AccumulatedFrames` of the DXGI images, the frames the DWM made; an image that stands for more than one frame means the loop took fewer images than the DWM made; `tick_late`: iterations that started 2 ms or more after their slot). `video pace` line every second while the video runs: `period_ms interval_ms enc_floor_ms enc_par enc_cpu_cores budget_cores cores process_cpu_cores slots slot_late slot_late_ms_max slot_resync`.

## 13. Sharpening and quality control of the H.264 video

Why: a measurement found 63-70 % of the bytes of an H.264 session in sharpening and the QP on the floor; the log of the agent showed the cause: the settle rule "150 ms without a change" compared `(DWORD)(gA.now - t->lastChange)`, but a tile painted by a video frame is stamped with the clock AFTER the encoder, so the difference was negative (about 4.29e9 unsigned) and every painted tile was sharpened at once and became a video tile again with the next frame.

- **Signed time comparison** (`common/kvm_sharpen.h`, `kvm_adapt.cpp`): the comparison is signed (`kvm_sharp_settled`); a time stamp later than `gA.now` means "changed just now". `gA.now` is read again after the encoder, before the sharpening. The other comparisons of times in `kvm_adapt.cpp` (`lastContentChange`, `streak`, `kvm_adapt_class`, the settle statistics) are signed too; `settle_ms_avg` in the log is in milliseconds again. `tile.cpp` and `kvm_video*.cpp` have no such comparison (their time stamps are all taken before the clock they are compared with).
- **Sharpening bucket** (`common/kvm_sharpen.{c,h}`, only while the video runs): while the video moves (a frame went out, or tiles are pending, in the last 300 ms) the sharpening pays from a bucket of 20 % of min(delivery rate, the viewer's budget) with a burst of 250 ms; the window is looked at before EVERY packet (inflight < 0.5 W) and one iteration sends at most a quarter of W. When the video is still the full budget is back (the picture converges as before). Forced sharpening pays from the same bucket and is never refused by it. Log: `adapt sharp_gov` (kb in a movement / outside / forced, refusals).
- **A quiet region instead of a quiet tile** is NOT done: on the gradient of the measurement the sharpening inside the movement is 4 % of the bytes after the signed comparison (8-9 KB/s); with half of the tiles quiet for stretches the bucket holds it at 20-23 %.
- **QP and the window of the viewer** (`common/kvm_video_rc.c`): the QP does not go down in a window in which the window of the viewer refused a frame; the sharpening that went out during a movement is debited from the bucket of the video and taken off R by the regulator (`kvm_vrc_note_sharpen`). Log: `qp_blocked`, `sharpen_share`.
- **Key frame log**: the log line `video idr reason=first|op3|broken|encoder ...` for every key frame (frame number, QP, size, time at the link, time since the previous frame and key frame, number and flags of the op 3, the time from the op 3, the time between the last two op 3 (a regular 10 or 30 s is the recording), the spacing rule). The QP of a key frame is max(QP of the P frames, the QP at which it fits in 0.3 s of R), 26..38 (was QP - 4, 22..38, 0.75 s).
- **QP on Windows 11 build 26200** (`common/kvm_qpdet.{c,h}`, `kvm_video.cpp`, `mf_h264.cpp`): the detector watches the frames the agent makes (the QP asked for, the QP the encoder reports in the output sample attribute `MFSampleExtension_VideoEncodeQP`, the size) and, when no step of the QP changes the size, gives a deliberate step of 4 for 5 frames after 40 frames without a verdict. Verdict INEFFECTIVE: stage 1 = the QP also in the input sample (`MFSampleExtension_VideoEncodeQP` on the input; documented by Microsoft only as an output attribute, so whether it works is what the tool says), stage 2 = the bit rate (a new encoder in the CBR mode, then LowDelayVBR, then PeakConstrainedVBR if the encoder refuses a mode; `AVEncCommonMeanBitRate` follows R during the stream, which Microsoft allows on Windows 8 and later; a new generation, like a change of the size). Log: `video qp ineffective`, `video qp effective`, `video bitrate mode`; `qp_stage`, `qp_verdict` in `video rc`.
- **Tool:** `kvm_h264_check qpsample` (also `probe --qpsample`): about 10 s, 1280x736, no desktop session needed. It tries the QP through the codec API, the QP also in the input sample, the sample attribute alone, and the bit rate of CBR / LowDelayVBR / PeakConstrainedVBR / UnconstrainedVBR set during the stream, and prints the size of the P frames before and after the change and the raw QP attribute of the output sample.
- Tests (Docker): `common/tests/run-kvm-sharpen-tests.sh`, `run-kvm-qpdet-tests.sh`, `run-kvm-video-rc-tests.sh`, the simulation `run-kvm-h264sim-tests.sh` (the model of the measurement and the steps), mutations `run-kvm-sharpen-mutations.sh`, `run-kvm-qpdet-mutations.sh`, `run-kvm-video-rc-mutations.sh`; the glue in `Windows/tests` (harness and its mutations).

## 14. Smoothness of the hybrid model

Why: a session on a laptop with an AMD GPU (open lid, High) showed 60 frames a second in continuous motion but stutter in the work with an interface (series of 0.2-0.5 s with pauses): the video started cold after every pause longer than 2 s (R 4 Mb/s, window 64 KiB), animations and the edges of dragged windows went out as JPEG (17.4 JPEG paints a second against 6.0 of the video), the sharpening took 29-99 % of the bytes of the seconds with motion. Automatic lowering of High is not done by design; typing stays JPEG (always sharp).

- **Proof of the first key frame** (`common/kvm_video_rc.{c,h}`): a session that began with a trickle of rate samples (33 B/s: positions of the size of a marker on a screen that stands) sized the window of the viewer at 64 KB, the first key frame (228 KB) was then followed by refusals of the window (`link_limited`), and R took 0.85 x 33 B/s as the capacity: 100 kb/s, a bucket in debt for 7 s and the video starved for 12 s (measured on a Windows 11 VM). Before the rate memory (next item) the ACK of the key frame was itself a rate sample; `busyFrom` does not take a sample across the silence before a period of work, so nothing lifted the estimate. Now the acknowledgement of a key frame is a proof of capacity (`capFloor`: 0.85 x bytes / (time to the ACK less the hold of the viewer), no round trip taken off), R is not below it for 60 s while the link is not full (the rule of the size of the key frame: refusals in 6 of the last 40 windows), a refusal of the window takes it away at once; and the estimate itself is never below the smallest R, so the probing (a quarter a second, in integers) cannot freeze at 30 B/s. Rate samples (`kvm_stream.c`): they follow the rule of BBR and GoogCC for app-limited samples, which replaced the filters on the bytes of the span (4 KB), on the rate (25 KB/s) and on the first key frame. A span in which the pipe was empty at some moment (`emptySince` not before the start of the span: the sender had nothing to send) and which the window did not hold back is a lower bound of what the link takes. It can raise the estimate and the remembered rate and never lowers them, and it is no evidence that the link is the limit: a refusal of the window while the estimate is made only of such lower bounds (a cursor and a caret, 5 - 8 KB in 850 ms; light work; the markers of a screen that stands) is a refusal of a window that was too small (`kvm_stream_note_link_held` returns 0, `kvm_stream_link_limited` is false, R is not taken from the trickle and the proof of the key frame stays: R 100 kb/s, 4 / 139 frames, a starved new key frame after 300 s of idle, a Windows 11 VM). A span in which the window held the sender back or the pipe never emptied (a clogged link) is what the link takes and counts at any rate, also a slow one (128 - 256 kb/s: the window is 64 KB, not the 256 KB of the start, 16 s of queue). The first estimate of R is the default 2 Mb/s: a rate that is no evidence of the link only raises it. The remembered rate is evidence of the link only while it is held (30 s): after minutes of idle it has decayed to a few B/s and a refusal of the window behind a new key frame does not take R from it. Every acknowledged key frame arms the proof again, so with periodic key frames (recording, every 30 s) R goes up to the ceiling of the estimate (2 x 0.85 x the remembered rate, which includes the bytes of the key frame) at each of them, which is higher than before the first key frame proof (and than the version before it: 13 against 4 Mb/s on a LAN in the simulation); only the first key frame without samples is no higher than before. R is the cap of the video bucket and QP, the window of the viewer still bounds the queue. The log: `video idr acked ... floor_bps=` (the proof; 0 when there is none) and `video rc ... r_from_floor=` (R of this second is higher than it would be without the proof: 0 when the budget of the viewer holds R at or below the estimate, or the proof is not used) with `floor_kbps=`.
- **Rate memory** (`common/kvm_stream.{c,h}`): the rate that sizes the window and R is remembered as the highest rate that was seen (`rateMem`, a maximum filter); it is kept 30 s without a confirmation, then halved every 30 s, cleared by a real stall (no ACK for 2 s with data in flight) and by a probe whose round trip has doubled. `kvm_stream_rate_or_mem` is the larger of the samples of the last 2 s and the memory, unless the window held a video frame or a big JPEG rectangle back in the last second (then the samples are what the link takes). A rate sample never spans the silence between two series (`busyFrom`: a write into a pipe that was empty for 500 ms begins a period of work), so a burst of 0.3 s is no sample. The window while only the memory sizes it is at most `KVM_STREAM_W_RESUME` (256 KiB): the link may have changed in the pause. The check of the resume: when a period of work begins on the memory alone, the first acknowledged position that had at least 64 KB in flight when it was written gives a delivered rate (flight / (time to the ACK less the hold of the viewer and the round trip)); below half of the remembered rate the memory becomes it, so the window and R follow the new link at once. R follows the rate, so a new series starts with the remembered window and R, not with 64 KiB and 4 Mb/s.
- **Class of a tile while the video runs** (`common/kvm_motion.{c,h}`, `kvm_adapt.cpp`, only while the video runs): the class of a tile is motion when it changed twice in a row while a frame with at least 16 real changes was seen in the last 250 ms (not "in the frame before this one"), or when it is within `KVM_ADAPT_VIDEO_NEAR` = 2 tiles (64 px) of a tile that was motion by the first rule in the last 250 ms (the first change of the edge of a dragged window, the next frame of an animation). A tile taken by the near rule does not extend the area. Third rule, the memory of the place (`KVM_ADAPT_VIDEO_RECALL_MS`, 3 s): the first change of a tile whose own last motion (the first rule) is younger than that is motion too (it does not stamp itself): an animation that comes back where the last one was starts as video, not as a JPEG of 300 KB. Everything else is JPEG: typing, the caret, a window that appears where nothing moved lately. `kvm_adapt_class` has the place of the tile (`row, col`). Soft text within 64 px of a motion lasts until the sharpening (about 0.2 s after the motion).
- **Movement and sharpening** (`common/kvm_sharpen.{c,h}`): a frame with at least 16 real changes is a movement however it went out (JPEG too), a movement lasts max(3 frame intervals, 100 ms) instead of 300 ms (`kvm_sharp_set_interval`), and for a second after it the packets of the sharpening go only while inflight < 0.25 W (`kvm_sharp_window_ok_at`), then 0.5 W again.
- **Change of the pixel source** (`kvm_motion_note_change`, `kvm_adapt_note_source`, `tile.cpp`): the first complete frame from another source of pixels (the fill from GDI, then the first copy of DXGI; a probe of DXGI; DXGI to GDI) is not motion: no streak, not counted as a moved tile or as a frame of motion, and a full-class rectangle of it that the window holds back stays full class (`deferred = 2`). No key frame of the whole screen and no sharpening of it at the start. The cause of the difference between the GDI fill and the first copy of DXGI (2022 of 2040 tiles) is the 4th byte of the pixel, which the tile hash counts: DXGI delivers it as 0 and GDI leaves its own; the 4th byte is now zeroed after `capture_full_gdi` and after `GetDIBits` (`kvm_clear_alpha`). A tile that still differs on a source change is not sent: the viewer is taken to have it and the tile is marked lossy, so the sharpening repaints it behind the motion (`kvm_motion_source_absorb`). Log: `adapt source_change tiles_differ= tiles= alpha_cleared=1`.
- **Write gap** (`common/kvm_video_core.c`, `kvm_video.cpp`): a frame is also not encoded before its write would be 75 % of the frame interval after the write of the previous one (the encode time to expect is the average, at most half the interval); the loop wakes for that (`kvm_video_wake_ms`). No more frames right behind a late one.
- **Series statistics** (`common/kvm_motion.c` `kvm_series_*`, `kvm_adapt.cpp`): one line every 10 s with the statistics of the series of motion (a series: a frame with at least 16 real changes after 500 ms without one): `video burst series= no_video= start_ms_avg= start_ms_max= r_kbps_start_min= paints_jpeg= paints_video= jpeg_pct= tiles_jpeg= gaps= gap_p95_ms= gap_max_ms= gap_over2x= interval_ms= class_streak= class_near= class_plain=`. `start_ms` is the time from the first frame of motion of a series to the first video frame; a gap is the time between two pictures written in a series (a video frame, or the JPEG rectangles of an iteration; the writes of one iteration closer than 4 ms are one picture); `jpeg_pct` is the share of the JPEG paints among the paints of the series.
- Tests (Docker): `common/tests/run-kvm-stream-tests.sh` (T1), `run-kvm-motion-tests.sh` (T2, T4, T7), `run-kvm-sharpen-tests.sh` (T3), `run-kvm-video-core-tests.sh` and `run-kvm-pace-tests.sh` (T6, with a model of a loop that overruns its slot), the glue in `Windows/tests` (harness), and the simulation `run-kvm-tune-sim-tests.sh` (the work with an interface on a 40 Mb/s link, built against the tree for the rows "after" and, when `OLD_COMMIT` names an earlier commit, against its files for the rows "before"; with the checks of the criteria of 7.9 for Docker); mutations `run-kvm-stream-mutations.sh`, `run-kvm-motion-mutations.sh`, `run-kvm-sharpen-mutations.sh`, `run-kvm-video-mutations.sh`, `run-kvm-pace-mutations.sh`, `run-kvm-tune-sim-mutations.sh`.

## 15. The encoder in a thread of its own

The video frame is made by a thread of its own while the main loop goes on with the next picture.

- **Who does what.** The main loop plans the frame (window, pace, bucket, QP, key frame, `kvm_vtiles_make_rects`), takes its tiles out of the model (`kvm_vtiles_dispatch`: INFLIGHT, a mask of the frames in flight on every tile) and hands the picture over (`kvm_encthr_submit`). The encoder thread (`kvm_encthr.cpp`) is a function of the job: picture (read only), key frame / QP / bit rate -> access unit or error. The result is collected by `kvm_video_service()` (the top of the iteration, while the loop waits for the capture in `kvm_capture_wait` or sleeps: they wait on the event of the encoder as well), checked and written by the main loop; only then the tiles land (`kvm_vtiles_land`, `tiles_painted` leaves the tiles that changed meanwhile alone: `paintCrc`).
- **Backend.** The encoder behind the thread is a table `kvm_encbe` (name, caps, the calls of `mf_h264.h`): `kvm_encbe_mf.cpp` is the software MFT, a hardware MFT is another table. `kvm_encthr_call(fn, arg, ms)` runs any function on the encoder thread (open, close, enumeration); that thread never calls SetThreadDesktop.
- **Barriers.** A JPEG of a tile that a frame in flight covers (`kvm_video_before_jpeg`, from `get_tile_at`), a REFRESH, a repair and a change of the QP stage wait for the frame (at most one encode, watchdog `KVM_ENC_WATCHDOG_MS` 1000 ms). Frames that the loop gives up (stop, new generation, error) are cancelled; what follows is a key frame.
- **Picture that waits.** When the encoder is busy, the window or the bucket is closed or the slot has not come, the newest picture is held (`gV.held`, a reference) and the frame starts when it can, not an iteration later. The gates of the JPEG and of the sharpening count the access unit in the encoder (`kvm_stream_set_reserved`).
- **Pictures.** `kvm_fbuf` (reference count, cache of 3, registry): the capture thread gets them (`KVM_BUF_GET` in `tile.h`), the loop and the job give them back.
- **Switches.** `MESH_KVM_ENC_THREAD=0`: the job is made in the call that hands it over (the behaviour before the encoder thread); `2` is the manual mode of the tests. Log: the line `video enc` (barriers by reason, busy_held, late_starts, cancelled, hung) with `video stats`; `video error backend=... structural=...`.
- **Hang.** A frame in the encoder for more than 1000 ms, or a call that does not return: the encoder is given up for good (`encoder_hung`: the thread, the picture and the frame buffer are leaked on purpose), the tiles go back to JPEG, the video is off for the rest of the process (as after a structured exception); the next KVM process starts again.
- **Tests (Docker).** `common/tests/run-kvm-encjob-tests.sh`, `-fbuf-tests.sh` (+ TSan), `run-kvm-video-core-tests.sh` (the INFLIGHT model with a canvas of the viewer), `Windows/tests/run-kvm-encthr-tests.sh` (the real thread with ASan and TSan), `run-kvm-video-harness.sh` (the glue with the manual thread, 1000 random sessions, the real thread plain and under TSan), the mutation scripts next to them.

## 11. DXGI silent: switching the capture to GDI and back

**The case.** A laptop with the lid closed (internal panel off, AMD GPU): the duplication of `\\.\DISPLAY1` is created, `AcquireNextFrame` times out for the whole session (`dirty_rects=0`), GDI sees every change. Before the capture source choice the comparison with GDI
(every 10 s, two differences, the duplication created again, then `stale_systematic` for the life of the process) gave one picture per ~20 s and then none at all: the code did not tell "DXGI shows it differently" from "DXGI shows nothing".

**Where it is.** The decisions are in `meshcore/KVM/common/kvm_capsrc.{h,c}` (portable C99, injected time, unit tests and a simulation in `common/tests/kvm_capsrc_test.c`, mutation check `run-kvm-capsrc-mutations.sh`); `tile.cpp` measures and does what it says
(`kvm_dxgi_frame`, the helpers `cap_*`), `dxgi_capture_describe_outputs()` lists the outputs for the log. The pixels of the picture are the same in both modes (the persistent full resolution image, the GDI path of `MESH_KVM_FORCE_GDI`): the size
and the format do not change, so the H.264 path (`kvm_video.cpp`, VIDEO tiles) sees only tiles that changed; there is nothing to restart when the source changes.

**Rules.**
- *Silent*: no image since the duplication was opened (the first full copy does not count) and the persistent image differs from a GDI capture, twice, 1 s apart (one difference is enough in a probe). A static screen never switches (no difference, no evidence).
  If the persistent image began as a DXGI full copy, only a difference that *changes* between comparisons counts (a constant colour difference is HDR, not silence). The comparison runs after 2 s, then at 5 s and 8 s (only while nothing has arrived), then every 10 s, only after 1 s without an image:
  at most the cost before the capture source choice plus three comparisons per opening of the duplication and one confirming comparison per difference. Typical time to GDI from the first change with the lid closed: 3 s after the open (about 4 s if a first frame came).
- *Differs* (images arrive, GDI differs; or DXGI went quiet after images): as before, the duplication is created again once, then `stale_systematic` (measure and log only). The latch ends when the pictures agree again, after 5 min, on a new desktop or geometry, and a
  picture that changes without any image while the latch is set (the signature of silence) switches to GDI.
- *GDI mode*: every frame through GDI. After 5, 10, 20, 40, 60 s (cap 60 s) a probe: the duplication is created again (new factory, the outputs are listed again, so an inactive output (`AttachedToDesktop` = false) or a new active output is found), and for at most 4 s the module judges it. Success: an image
  after the first full copy, and when the pictures were compared (>= 1 s) they agree (or the 4 s ran out with images): DXGI is the source again, the pause starts at 5 s again. Failure: silent again after 0.6 s (the picture is stale for that long at most), or the duplication cannot be created: GDI, longer pause.
  Inconclusive (static screen): DXGI stays, the pause is not forgotten. A new geometry or desktop makes a probe due at once. Failing to create DXGI three times (`strikes`) is no longer for the life of the process: GDI and probes. `MESH_KVM_FORCE_GDI`, an exception, and an old system without DXGI still disable it for good.

**Log** (`MeshAgent-kvm.log`, all lines in the log of the capture source choice start with `capture` or `dxgi stale`):
`capture mode=gdi reason=dxgi_silent retries=<failed probes> px= box= updates= since_open_ms= since_image_ms= next_probe_ms= outputs="<adapter>|<output> l,t,r,b att=<0|1> rot=<n>;..."`,
`capture probe try=<n> retries= gdi_ms= outputs=`, `capture probe failed reason=dxgi_silent|<dxgi result>|not_open retries= next_ms=`, `capture mode=dxgi reason=recovered gdi_ms= probes= updates= total_gdi_ms=`, `capture probe inconclusive`, `capture reset why=desktop|geometry`,
`dxgi stale_suspect|stale|stale_systematic ... kind=silent|differs updates= since_open_ms= since_image_ms=`, `dxgi stale_systematic_cleared reason=equal`; the probes are logged in full for the first 12, then every tenth. `stats` has `cap_mode=<dxgi|probe|gdi> cap_to_gdi= cap_probes= cap_probe_fails= cap_recovered= cap_inconclusive=`
(events in the period; `path=` still says where the frames came from). Confirmed cause on the next try: `capture mode=gdi reason=dxgi_silent ... updates=0` and in `outputs` the panel `att=1` or not; after waking the screen `capture mode=dxgi reason=recovered`.
Tunables: `/DKVM_CAPSRC_*` (kvm_capsrc.h). Not changed: the cost of GDI at 1920x1200 (GDI mode costs what `MESH_KVM_FORCE_GDI` costs, also on a still screen).

## H.264 encoder probe

`common/kvm_yuv.{c,h}` (BGRA to NV12, BT.709 limited range, SSE2 and scalar, bit identical, negative stride for bottom-up bitmaps), `common/kvm_annexb.{c,h}`
(access unit clean-up: removes access unit delimiters, puts SPS+PPS in front of every IDR; portable C, tests in `common/tests`, run with `run-in-docker.sh`),
`Windows/mf_h264.{h,cpp}` (C interface around the software Microsoft H.264 Encoder MFT; mfplat.dll, ole32.dll and RtlGetVersion are loaded at run time, the
import table of the tool is only kernel32, user32 and gdi32) and `Windows/tools/kvm_h264_check.cpp` (`probe`, `bench`, `dump`, `gentest`).
Build: `cl /O2 /MT /EHsc /utf-8 /D_CRT_SECURE_NO_WARNINGS mf_h264.cpp kvm_yuv.c kvm_annexb.c kvm_h264_check.cpp /link user32.lib gdi32.lib`.

Rules of the wrapper (details in `mf_h264.h`):
- Preset: rate control Quality, constant quantizer per frame with `AVEncVideoEncodeQP` as VT_UI8 (QP in the three 16 bit fields I, P, B), B-frames 0, low latency,
  GOP = the largest value (only IDR pictures that were asked for). No automatic choice of the QP form at run time (the tool's `qpcheck` detects it).
- The nominal frame rate in the media types is 30 fps; the level is computed from the macroblock count and set explicitly (3.0 ... 5.2; above 36864 macroblocks
  or above the viewer's maximum level: `MFH264_E_LEVEL`); the profile and level the encoder wrote are read from its SPS. Sizes are multiples of 16.
- Every access unit that is returned follows the protocol: no access unit delimiter, an IDR starts with SPS and PPS. A frame that gives no usable access unit
  (no output, a second output, an unfinished split output, an access unit bigger than the buffer or `max_au_size`, malformed output) returns `MFH264_E_STREAM_BROKEN`;
  the encoder is flushed and the next frame is an IDR. `mfh264_max_au_size()` is a buffer size that cannot overflow.
- Every call into Media Foundation is guarded by `__try/__except` (MSVC). After an exception `mfh264_faulted()` is 1, every call fails at once, and `mfh264_close()` /
  `mfh264_shutdown()` do nothing (leak on purpose).

was and `--hw` answers with a usage error). Needs no desktop, no capture, no KVM session, no network; reads nothing but the machine's own display mode and adapter list.

  with the setting changed in the middle of the stream, the size of the P pictures, and the QP that the output sample reports.

## 15. Hardware H.264 encoder

The GPU's own encoder (a hardware Media Foundation transform, e.g. `AMDh264Encoder`) as a second encoder backend next to the software MFT. **On by default, only after a self test of this machine, with the software encoder as the way back.** The wiring into the video code (`kvm_video.cpp`) comes after the encoder thread; what is here:
- `mf_h264_hw.cpp`, `kvm_encbe_mfhw.h`: the backend (`kvm_encbe_mfhw`, the table of `kvm_encthr.h`). Asynchronous MFT (`MF_TRANSFORM_ASYNC_UNLOCK`, a thread that waits for the events, one input per `METransformNeedInput`, `ProcessOutput` after `METransformHaveOutput`, its own output samples), a deadline on every wait (250 / 500 / 2000 ms) and a handle that is dead after one (it is never called again and never released), a flush that forgets the credit and the events, QP only as `AVEncVideoEncodeQP` VT_UI4 / FrameTypeQP / `AVEncCommonQuality` with the rate control Quality (the packed UI8 form of the software encoder is refused by the AMD MFT), the SPS from the IDR, a fault flag of its own (an exception in the driver does not switch the software encoder off). No `AVScenarioInfo` (it only made the encoder slower).
- `kvm_hwtest_core.c`, `kvm_hwtest.cpp`: the self test. `MeshService64.exe -kvmhwtest W H level maxLevel profile luid rev key` (ServiceMain.c) is a short process of its own that the KVM child starts in the background (the child's token, session and desktop; a job object that kills it with the child, 25 s, 512 MB). It encodes 20 synthetic pictures of the size of the screen (all but the last two as a session with the view does it, as the NV12 picture of `encode_nv12`; the last two as BGRA, the way of `MESH_KVM_NV12_FROZEN=0`) and checks the 15 rules of the viewer, the colour (full range or another colour space is refused; 0 / 0 / 2 as the AMD encoder writes it is not), the effect of the QP (26 against 40: more than 1.4 times), a key frame that is asked for (in that frame), 1 : 1, and the time (median 25 ms, 95 % 60 ms, key frame 250 ms: too slow is the verdict SLOW, tested again after 24 h). After the plan a flat key frame is encoded (by the view): its size is only the floor of a flat key frame (`flat=`, information for (B)), but a hang or an exception on it is a failure (rule `flat`), because a lock screen is such a picture. `KVM_HW_SELFTEST_REV` is 3 (2 = the frames of the view and the flat key frame), so every machine tests once more after the update. an encoder that fails the QP rule (or takes no QP form) is tried again with the bit rate: open with CBR (LowDelayVBR when the open refuses CBR), `set_bitrate` 8 / 4 / 1 Mb/s (at 1920x1088, scaled by the area and never above what the level allows) in place of the QP 26 / 30 / 40, the same rule (P at the high rate more than 1.4 times P at the low one; rule `rate`). It passes as form 8 (CBR) or 9 (LDVBR) in the field `qp=` of the cache. A session then runs the hardware encoder in stage 2 (the existing path of the software encoder: the bit rate steers, no QP, no Auto of the agent: no caps bit 2, the interval of Auto is 0), and the hardware encoder in the bit rate mode wins over the software one after a passed self test, also where the software encoder listens to the QP. Revision 5 (`KVM_HW_SELFTEST_REV` 5): the GOP is read back after it is set (NVIDIA answers S_OK to 0xFFFFFFFF and keeps 30): candidates range maximum, 0x7FFFFFFF, 0xFFFFFFFF in the order A (types, then the codec API); when none holds, a new encoder in the order B (the codec API, then the types); when it still reads <= 10000 the open fails and the self test says `gop`. In a session a second key frame that nobody asked for gives the hardware up (`periodic_idr`). Revision 6 (`KVM_HW_SELFTEST_REV` 6): the pass `qp` has the plan of the pass `rate` (a key frame, 14 pictures of pay back at QP 30, 12 at 26 and 12 at 40, measured from the 4th picture of a window), because NVIDIA in the order B takes the QP at the open only and ignores a change; in a session `qp_ineffective` on the hardware encoder with the QP form opens the same encoder again once in the form 8 (stage 2, CBR) and writes the form 8 into the cache entry of the key, and only an error of that try gives the hardware up. When the hardware encoder is given up the software one starts at stage 0 and the Auto of the last op 1 (`autoWant`) is the agent's again. Result as text on stdout, exit code 0 / 1 / 2.
- `common/kvm_hwpolicy.c`: the cache `<exe>-kvmhw.txt` (verdicts by key: encoder, adapter, driver, Windows build, revision of the test `KVM_HW_SELFTEST_REV`, token class, size class; four entries; the errors of sessions with a time to live of 14 days; the marker of a try that crashed), the decision with a reason (`env_off os no_hw size mode_sw process_disabled bad_persisted gdi_no_output winlogon test_running slow test_done cached test_started`), the key and the result.
- The QP: the regulator keeps the scale of the software encoder (26 to 38); the hardware encoder is given `kvm_vcore_hw_qp` = QP - 4, never below 26 (its "QP 30" looks like QP 34 of x264, and it is thought to clamp below 26); the regulator's floor is 30 for it (`kvm_vrc_set_backend`). The prior and the slope of the key frame are the software ones (12.5: its key frame is 8 % smaller). `kvm_qpdet_set_probes(d, 0)` switches the deliberate QP steps off.

**Switches.** `MESH_KVM_VIDEO_HW` in the environment of the service: unset or `1` = auto (the default), `0` = off, `force` = also try after the entry became "bad". The file `<exe>-kvmhw-mode.txt` (next to the executable, e.g. `C:\Program Files\Mesh Agent\MeshAgent-kvmhw-mode.txt`) with one word, `auto` / `sw` / `hw`, is read when a KVM process starts and is never written by the agent: **`sw` works with the next session (the next KVM child), no service restart**, and can be written by a remote command, e.g. `cmd /c echo sw> "C:\Program Files\Mesh Agent\MeshAgent-kvmhw-mode.txt"`; deleting the file or writing `auto` brings back the default. The cache file is only a cache: deleting it means "test again".

**Capture file.** `<exe>-kvm-capture.txt` (next to the agent executable, like the mode file): its first word `gdi` turns DXGI off for the KVM process like `MESH_KVM_FORCE_GDI=1`; no file, `auto` or any other word changes nothing. Read when the KVM process starts (the next session, no service restart), never written by the agent. The line `start` of the log has `file_force_gdi=0/1` next to `env_force_gdi`, the line "dxgi disabled" says `reason=env` or `reason=file`. Remote: `cmd /c echo gdi> "C:\Program Files\Mesh Agent\MeshAgent-kvm-capture.txt"`, back with `cmd /c del` of the same file.

### 15.1 The hardware encoder in the video code (`kvm_video.cpp`)

- **Which backend, and why.** For every new encoder (`attempt_start`, a new size, the retry) `hw_choose` asks `kvm_hwp_decide` (the switches, the system, the capture mode, the desktop, the cache) and logs the answer: `video backend be=hw|sw why=<reason> hw_name=… adapter=0xVEN:0xDEV drv=…` and `video hw key=…`. The mode file is read for **every generation**, so `sw` takes effect with the next one, not only with the next session. The inline mode of the encoder thread (`MESH_KVM_ENC_THREAD=0`) never uses the hardware encoder.
- **The self test never delays a start.** With no verdict in the cache the software encoder runs and `kvm_hwtest_start` starts the test in the background (`video hw self test started`); `kvm_video_poll` collects the result without waiting (`hw_poll_test`), checks its key, writes it to the cache. When it has **passed** while the software encoder runs, the next quiet moment (no frame in flight, no pending tile, no frame for a second, the limit of one encoder in 2 s respected) starts a new generation on the hardware encoder (`video hw switch`, `START_BACKEND`): a new 242, an IDR, the tiles as JPEG meanwhile.
- **The hardware encoder runs on its own thread backend.** `kvm_encthr_start` with `kvm_encbe_mfhw` (a new thread, which never calls `SetThreadDesktop`); the QP that it is given is `kvm_vcore_hw_qp(QP of the regulator)`, everything that remembers a QP (the rate control, the prediction of the key frame, the detector, the log) has the regulator's. `kvm_qpdet` has no deliberate steps for it and expects 8 % per step.
- **The way back.** An error of the hardware encoder in a session (`E_HANG` or a deadline, a frame that failed, three lost access units in a row, a QP that has no effect, an encoder that does not open, a hang found by the watchdog) writes the error into the cache (weight 2 for a hang / exception, 1 otherwise), closes the encoder and starts **one** new generation on the software encoder, not held back by the limit of one open in 2 s; the hardware encoder is off for the rest of the process (`why=process_disabled`). **An exception in the driver ends this KVM process** after the counter is written (exit code 0x4857): the service starts a new one, as after UAC. A hang that is found when the thread is already given up leaves that thread and its buffers to the process and starts a new thread with the software backend.
- **The marker of a try** is written before the hardware encoder is opened and cleared after its first written access unit. The service (the parent) decides what an unfinished marker is: `kvm_cleanup` and `kvm_relay_ExitHandler` call `kvm_hwtest_child_gone(pid, exit code)`: the end of a session (1067) clears it, a status of a crash (>= 0xC0000000) is an exception; a marker that nobody resolved is one error (found at the start of the next process).
- Log: `be=` in `video rc` and `video stats` (`hw_disabled`, `hw_why`); `video hw fallback why=… weight=…`, `video hw exception …`, `video hw self test verdict=… rule=…`.

## 16. The NV12 view of the encoder

The encoder is not given a fresh conversion of the whole screen at every frame. The thread of the encoder owns a persistent NV12 picture, the **view** (`common/kvm_nv12view.{c,h}`, `kvm_yuv_bgra_to_nv12_region`). The viewer paints only the rectangles of a frame from the decoded picture, so what the encoder sees outside them decides nothing but the size of the frames and how 1-3 pixels at the edges look.

- **(A) frozen** (`MESH_KVM_NV12_FROZEN`, default **on**; compile time `KVM_NV12_FROZEN_DEFAULT`): a key frame converts the whole picture, every other frame only the macroblocks of its rectangles plus a ring of one macroblock (16 px) around them, where the deblocking filter reads the neighbours. Outside the view stays as it was: the P frames carry no residual for changes that are sent as JPEG. Saves the conversion of the whole screen (1.4-3 ms) at the price of a copy of the view into the input buffer of the encoder (about 0.3-0.5 ms).
- **(B) flat key frame** (`MESH_KVM_IDR_FLAT=1`, default **off**; `KVM_IDR_FLAT_DEFAULT`; needs A): at a key frame the view is first made one flat colour (the dominant colour of the picture) and only the rectangles of the frame, the tiles that the viewer shows from the video (VIDEO or in flight) and their rings are converted, so the key frame is proportional to that area. The macroblocks that are touched for the first time after it are "virgin": they cost about their intra size once, and the rate control reserves and discounts them (the QP detector does not see those frames). `MESH_KVM_IDR_FLAT_FIRST_FULL` (default 1): the first key frame of a session stays complete (the proof of throughput of the first key frame).
- The plan runs in the loop (`kvm_nv12v_plan`) and travels to the thread **as a copy**: `kvm_ej_submit` copies the map (mbCols x mbRows bytes) into the slot of the job, and the job that the thread takes has `viewMap` pointing at that copy, which nothing writes until the job is finished; no pointer into the memory of the loop reaches the thread, and the job is not bigger than before (the map is not in `kvm_ejob`). A frame that is given up, lost or failed invalidates the view: the next key frame is complete. In (B) that holds for every key frame after the view was invalidated as long as `MESH_KVM_IDR_FLAT_FIRST_FULL=1` (the default): the only flat key frames are those of op 3 and of the recording when nothing has invalidated the view since the previous key frame (not the one of a new generation, of VIDEO OFF/ON, of a new size, of a lost or failed frame); with `FIRST_FULL=0` the key frame after an invalidation is flat, too.
- Log: `video view mode=frozen|flat frames= conv_us_avg= conv_mb_avg= complete= flat= virgin_mb=` next to `video stats`; the line of a key frame is `video idr view real_mbs= total_mbs= complete= flat= bytes= bytes_per_real_mb= forecast=` (the virgin macroblocks are counted in `video view` only).
- **Before (B) is switched on** (it is off by default, and these are the conditions, from a design review): (1) decide what `FIRST_FULL` means (the key frame after every invalidation, as now, or only the first one of an encoder) and test a key frame after `invalidate` with `FIRST_FULL=1` and `sessionIdr=1`; (2) a small flat key frame must not replace a better proof of throughput (`capFloor`, `cIdr` of `kvm_vrc_idr_acked`, `KVM_VRC_IDR_PROOF_MIN_BYTES` = 0): simulate a proof of 220 KB, a flat key frame of 10 KB 30 s later and then full-screen motion; (3) the spacing of the key frames after a small one (`kvm_vcore_idr_spacing(lastIdrBytes)`) with a complete key frame that may follow it; the floor of a flat key frame is 200 thousandths of a byte per macroblock (CABAC), the software encoder (profile 66, CAVLC) would need about 800 and is not measured by the self test, and `hw_choose` keeps the old `flatMilli` when the cache entry has another key; (4) a test of the key frame after a lost access unit with (B) on; (5) a measurement on a real encoder (a Windows 11 VM, a laptop with an AMD GPU).

## 17. Auto mode of the frame rate

The viewer's list of frame rates gets a fifth entry, **Auto**: bit 3 of the flags of op 1 (240). The agent announces that it knows it with bit 2 of the caps of every 242 (`KVM_CAPS_AUTO`, only with video, and not with `MESH_KVM_AUTO=0`, which also makes the agent ignore the bit). A viewer that sends the bit also sends command 5 with 33 ms (Medium) as the reserve: with the bit down, with an agent that does not know Auto, or while the video does not run (JPEG), that period is what holds, as before. Nothing in the protocol is new (no new command: op 7 and 244 are a later stage).

- **One actuator: the target interval of the frames**, 60 / 30 / 20 / 15 / 10 a second (16 / 33 / 50 / 66 / 100 ms), the same interval that command 5 sets in the fixed modes. `common/kvm_auto.{c,h}` (portable C99, tested in Docker) decides once a second; `kvm_video.cpp` feeds it and applies the step (`frame_period_ms()` and `kvm_video_loop_period()` for the pause of the loop in `kvm.c`). A step is **not** a new generation: no key frame, no 242, the media type and the level stay. The QP regulator, the window of the viewer, the byte bucket, the CPU budget of the encoder (the interval is still never below its floor), the sharpening of the JPEG tiles (the text at rest), REFRESH and the JPEG quality are untouched: **Auto never lowers the quality of the text at rest**; it only chooses the frame rate of the motion. Fewer frames at the same R are more bytes per frame, so the QP regulator lowers the QP by itself.
- **Rules**: a window of one second with at least 300 ms of motion is evaluated (a window without motion counts neither way). Down, two windows in a row: the machine does not keep up (the achieved rate under 75 % of the target with nothing held back and tiles waiting; the interval that the CPU budget of the encoder needs above the target; the P75 of the capture time, or of the gap between two images, above 4/3 of the interval; the last three not when the frames of the desktop manager show that the loop takes every image the source makes), straight to the step that holds the cost; or the QP of the regulator (plus the rise that the refused frames are about to cause) above the ceiling of the step, one step. Up, `upNeed` (4, 8, 16, 32, 64, 120 after a failed attempt, 4 again after a step up that held for 60 s; after a step down for the link at least 64, so a link that queued at a step is not tried again for 64 windows, a failed attempt doubles from there to 120) windows in a row with the QP of the motion at most the ceiling of the faster step less 6, under 5 % of the frames refused, under 100 ms in flight, the machine not limiting and the cost fitting the faster step. A key frame freezes its window and the following ones for the time it needs on the link. Start: 60 when the first minimum round trip is under 20 ms, else 30 (before that, and after 3 s without a round trip, 30). The class of content is always "UI" in this stage (ceilings 32 / 32 / 34 / 36 / 38).
- **A slow laptop** (a design decision of 2026-11-14): 45..55 frames a second are not a reason to leave 60 (the threshold is 75 % of the target); below 45 it is.
- **Where it hooks in.** `kvm.c`: the pause of the loop (`kvm_video_loop_period`), the capture time of an image before `kvm_video_emit` (`kvm_video_note_capture`), the caps bit in `kvm_stream_send_state_locked`. `kvm_video.cpp`: the bit in `handle_request`, the notes (`kvm_auto_note_image` in `kvm_video_emit`, `_held` in `try_start`, `_frame` / `_key` in `process_result`), the window in `kvm_video_poll` (`auto_tick`), the helper functions. `MeshService-2022.vcxproj`: `kvm_auto.c` / `.h`.
- **Log.** Every second with motion, and at every step: `auto on=1 step=… fps=… interval_ms=… changed=… reason=start|link|cpu|capture|back eval=… flags=… motion_ms made achieved_fps held_win held_rate held_pct qp_mean qp_end cap_p75_ms gap_p75_ms dwm_x100 need_ms cpu_streak qp_streak good_streak up_need changes downs ups`. Nothing is logged with the bit down.
- **Tests (Docker).** `common/tests/run-kvm-auto-tests.sh` (+ `run-kvm-auto-mutations.sh`), `run-kvm-auto-sim-tests.sh` (the real stream layer, rate control and pace in a closed loop with `kvm_auto`, 16 scenes, each also with the fixed Medium and High), the glue in `Windows/tests/kvm_video_auto_tests.inc` (the harness; its mutations are the `Auto mode` lines of `run-kvm-video-harness-mutations.sh`). The fixed modes are checked byte for byte: the hash of the stream of a scenario is the one of the code before Auto.
